2. AUTHENTICATION & AUTHORIZATION
================================================================================

2.1 AUTHENTICATION FLOW
────────────────────────────────────────────────────────────────────────────────

METHOD: JWT (JSON Web Token) via Supabase Auth
ALGORITHM: RS256 (asymmetric signing)
EXPIRATION: 
  - access_token: 1 hour
  - refresh_token: 7 days

JWT PAYLOAD (Claims)
{
  "sub": "uuid-user-id",
  "email": "user@example.com",
  "user_type": "customer|driver|merchant|admin|system",
  "phone": "+62812345678",
  "iat": 1723637400,
  "exp": 1723641000,
  "iss": "https://supabase-instance.supabase.co"
}

TOKEN DELIVERY
- Response: Authorization: Bearer <access_token>
- Request: Header Authorization: Bearer <access_token>
- Storage (Mobile): Secure enclave (iOS Keychain, Android Keystore)
- Refresh: POST /auth/refresh-token with refresh_token

2.2 ROLE-BASED ACCESS CONTROL (RBAC)
────────────────────────────────────────────────────────────────────────────────

USER ROLES (from users.user_type ENUM)
┌──────────┬─────────────────────────────────────────────────────────┐
│ Role     │ Capabilities                                            │
├──────────┼─────────────────────────────────────────────────────────┤
│ customer │ Book rides, order food, create send orders, manage      │
│          │ wallet, rate driver/merchant                            │
├──────────┼─────────────────────────────────────────────────────────┤
│ driver   │ Accept rides/food/send orders, update location, complete│
│          │ delivery, withdraw earnings                             │
├──────────┼─────────────────────────────────────────────────────────┤
│ merchant │ Manage store profile, catalog, accept/prepare orders    │
├──────────┼─────────────────────────────────────────────────────────┤
│ admin    │ Audit ledger, freeze accounts, approve withdrawals,     │
│          │ reverse transactions (chargeback)                       │
├──────────┼─────────────────────────────────────────────────────────┤
│ system   │ Internal: Process settlements, execute scheduled tasks  │
└──────────┴─────────────────────────────────────────────────────────┘

ENDPOINT-LEVEL RBAC
All endpoints validate:
1. Token validity (signature, expiration)
2. User status (ACTIVE, not SUSPENDED/FROZEN/DELETED)
3. Role requirement (e.g., customer-only endpoint)

RLS (Row-Level Security) enforced at database layer:
- SELECT: Users see only own data (id = auth.uid())
- INSERT: Wallet creation requires matching user_id
- UPDATE: Only own records can be updated
- Admin: Can query all via (auth.jwt() ->> 'user_type') = 'admin'

────────────────────────────────────────────────────────────────────────────────

HTTP Status: 4xx (client), 5xx (server)

Format:
{
  "success": false,
  "error": {
    "code": "ERROR_CODE",
    "message": "Human-readable error message",
    "details": { /* optional extra context */ }
  },
  "meta": { ... }
}

ERROR CODES (STANDARDIZED)

| Code                           | HTTP | Meaning                                       |
|--------------------------------|------|-----------------------------------------------|
| INVALID_REQUEST                | 400  | Malformed request, missing field              |
| UNAUTHORIZED                   | 401  | Missing/invalid token                         |
| FORBIDDEN                      | 403  | Token valid but role insufficient             |
| NOT_FOUND                      | 404  | Resource doesn't exist                        |
| CONFLICT                       | 409  | Race condition (e.g., order already assigned) |
| UNPROCESSABLE_ENTITY           | 422  | Business logic violation (e.g., KYC limit)    |
| RATE_LIMIT_EXCEEDED            | 429  | Too many requests                             |
| INTERNAL_SERVER_ERROR          | 500  | Unexpected backend error                      |
| SERVICE_UNAVAILABLE            | 503  | Database down or temporary outage             |
| IDEMPOTENCY_CONFLICT           | 409  | Same idempotency-key with different payload   |

Example (Error):
{
  "success": false,
  "error": {
    "code": "INSUFFICIENT_BALANCE",
    "message": "Wallet balance insufficient for transfer",
    "details": {
      "available": 100000,
      "required": 500000,
      "shortfall": 400000
    }
  },
  "meta": { ... }
}

4. COMMON HEADERS & VALIDATION
================================================================================

4.1 REQUEST HEADERS
────────────────────────────────────────────────────────────────────────────────

Required (All endpoints):
- Authorization: Bearer <access_token>
- Content-Type: application/json
- User-Agent: G-Flow/<platform>/<version> (e.g., G-Flow/mobile/1.0)

Optional (Idempotent operations):
- X-Idempotency-Key: <UUID> — Required for POST /wallets/*/topup, /transfer, 
                               /rides/book, /food-orders, /send-orders
  * Idempotency guaranteed for 24 hours
  * Same key + same payload = identical response
  * Same key + different payload = HTTP 409 IDEMPOTENCY_CONFLICT
  * Idempotency cache stored in Redis (AOF persistence)

Optional (Tracing):
- X-Request-ID: <UUID> — For request tracking (generated if missing)
- X-Correlation-ID: <UUID> — For distributed tracing

4.2 REQUEST VALIDATION
────────────────────────────────────────────────────────────────────────────────

All inputs validated server-side:

Numeric Fields
- balance, amount, fare: Must be >= 0, numeric precision to 2 decimals
- Use decimal.Decimal in Go (shopspring/decimal)
- Currency: All amounts in IDR (Rp) as integers (no decimals in JSON)

String Fields
- email: RFC 5322 compliant
- phone: +62 prefix optional, 10-15 digits, validated via regex
- UUID: RFC 4122 format
- Enum fields: Strict matching (e.g., order_status from ENUM list only)

Date/Time
- All timestamps: ISO 8601 with timezone (TIMESTAMPTZ in DB)
- Timezone: UTC (no client-side timezone)
- Format: "2026-08-14T10:30:45.123Z"

4.3 RESPONSE VALIDATION
────────────────────────────────────────────────────────────────────────────────

All responses guarantee:
- Consistent JSON structure (success/error/meta)
- Complete fields (no partial null objects)
- Type safety (no string where number expected)
- Enum values match database ENUM definitions

5. RATE LIMITING STRATEGY
================================================================================

TOKEN BUCKET ALGORITHM
- Window: 1-minute rolling window
- Per: User ID (authenticated) or IP (unauthenticated)
- Fallback: IP-based if auth fails

LIMITS BY ENDPOINT TYPE

| Endpoint Category          | Limit        | Tier      | Notes                   |
|----------------------------|--------------|-----------|-------------------------|
| Authentication (signup)    | 10 req/min   | IP        | Anti-spam               |
| Authentication (login)     | 20 req/min   | IP        | Anti-brute-force        |
| Read (GET)                 | 100 req/min  | User      | Non-blocking            |
| Write (POST/PATCH)         | 30 req/min   | User      | Financial operations    |
| Wallet operations          | 10 req/min   | User      | Topup/Transfer safety   |
| Ride/Food/Send operations  | 10 req/min   | User      | Order creation safety   |
| Driver accept order        | 30 req/min   | Driver    | Rapid accept attempts   |
| Admin operations           | 30 req/min   | Admin     | Audit operations        |

RATE LIMIT HEADERS
Response includes:
- X-RateLimit-Limit: 100
- X-RateLimit-Remaining: 87
- X-RateLimit-Reset: 1723641000 (Unix timestamp)

When Exceeded (HTTP 429):
{
  "success": false,
  "error": {
    "code": "RATE_LIMIT_EXCEEDED",
    "message": "Rate limit exceeded. Try again in 45 seconds.",
    "details": {
      "limit": 10,
      "window_seconds": 60,
      "reset_at": "2026-08-14T10:31:45Z"
    }
  }
}

6.2 TOP-UP FLOW (INTERNAL ONLY — NO THIRD-PARTY GATEWAY)
────────────────────────────────────────────────────────────────────────────────

POST /wallets/{wallet_id}/topup
  Auth: Required (user_type: customer, driver, merchant)
  Role: User owns wallet
  Rate Limit: 10 req/min per user
  Idempotency: REQUIRED (X-Idempotency-Key)
  
  Request:
  {
    "amount": 500000,
    "payment_method": "SIMULATED"
  }
  
  NOTE: payment_method MUST be 'SIMULATED' (internal simulation only).
        Third-party gateways (Stripe, GCash) out of scope for V1.0.
  
  Response: 201 Created
  {
    "success": true,
    "data": {
      "transaction_id": "uuid-txn-789",
      "user_id": "uuid-user-456",
      "amount": 500000,
      "status": "PENDING",
      "payment_method": "SIMULATED",
      "requested_at": "2026-08-14T10:30:00Z",
      "message": "Top-up initiated. Webhook will process."
    }
  }
  
  Errors:
  - 400 INVALID_REQUEST: Missing amount or invalid payment_method
  - 401 UNAUTHORIZED: Invalid token
  - 403 FORBIDDEN: User doesn't own wallet
  - 409 CONFLICT: Duplicate X-Idempotency-Key with different payload
  - 422 UNPROCESSABLE_ENTITY: Business logic violation (see below)
  - 429 RATE_LIMIT_EXCEEDED: Too many top-up attempts
  
  Business Logic Validations (422):
  1. KYC Limit Check (Bug #25, LOGIC_FLOW 1.2)
     - Unverified: max_balance = 2,000,000
     - Verified: max_balance = 20,000,000
     - Error: { "code": "KYC_LIMIT_EXCEEDED", "details": { "current": X, 
       "limit": Y, "requested": Z } }
  
  2. Overdue Debt Settlement (Bug #47, LOGIC_FLOW 1.2)
     - If customer.overdue_debt > 0:
       → Deduct from top-up amount to settle debt first
       → Only remainder goes to wallet
       → Return: { "debt_settled": X, "wallet_credited": Y }
  
  3. Wallet Status Check
     - Wallet must be ACTIVE (not SUSPENDED, FROZEN, DELETED)
     - Error: { "code": "WALLET_INACTIVE", "details": { "status": "SUSPENDED" } }

Webhook Processing (Internal — Database Trigger)
  After PENDING created, webhook polls topup_transactions table:
  - Status COMPLETED → HTTP 200 (idempotent)
  - Status EXPIRED + webhook SUCCESS → Allow late settlement (Bug #56)
  - Creates double-entry ledger:
    * DEBIT: SYSTEM_BANK_GATEWAY wallet
    * CREDIT: Customer wallet
    * reference_type: WALLET_TOPUP
    * reference_id: transaction_id

6.3 TRANSFER P2P
────────────────────────────────────────────────────────────────────────────────

POST /wallets/{from_wallet_id}/transfer
  Auth: Required (user_type: customer, driver, merchant)
  Role: User owns from_wallet_id
  Rate Limit: 20 req/min per user
  Idempotency: REQUIRED (X-Idempotency-Key)
  
  Request:
  {
    "to_wallet_id": "uuid-wallet-recipient",
    "amount": 100000,
    "description": "Payment to driver",
    "reference_type": "RIDE_SETTLEMENT"
  }
  
  Response: 200 OK
  {
    "success": true,
    "data": {
      "transfer_id": "uuid-transfer-999",
      "from_wallet_id": "uuid-wallet-123",
      "to_wallet_id": "uuid-wallet-recipient",
      "amount": 100000,
      "reference_type": "RIDE_SETTLEMENT",
      "from_balance_after": 1400000,
      "to_balance_after": 2100000,
      "created_at": "2026-08-14T10:30:00Z"
    }
  }
  
  Errors (400-422):
  - 400 INVALID_REQUEST: Missing required fields
  - 401 UNAUTHORIZED: Invalid token
  - 403 FORBIDDEN: User doesn't own from_wallet
  - 404 NOT_FOUND: Recipient wallet doesn't exist
  - 409 CONFLICT: 
    * Duplicate X-Idempotency-Key with different payload
    * from_wallet_id = to_wallet_id (Bug #27, LOGIC_FLOW 1.3)
  - 422 UNPROCESSABLE_ENTITY: Business logic violation
  
  Business Logic Validations (422):
  1. Self-Transfer Check (Bug #27)
     - Error: { "code": "SELF_TRANSFER_NOT_ALLOWED" }
  
  2. Sufficient Balance Check
     - Error: { "code": "INSUFFICIENT_BALANCE", "details": { 
       "available": X, "required": amount } }
  
  3. Source Wallet Status
     - Must be ACTIVE
     - Error: { "code": "WALLET_INACTIVE" }
  
  4. Recipient KYC Validation (Bug #46)
     - Check recipient wallet max_limit
     - Error: { "code": "RECIPIENT_LIMIT_EXCEEDED", "details": { 
       "recipient_balance": X, "recipient_limit": Y, "requested": Z } }
  
  5. Recipient Wallet Status
     - Must be ACTIVE
     - Error: { "code": "RECIPIENT_WALLET_INACTIVE" }

Implementation: Pessimistic Locking (LOGIC_FLOW 1.3)
  - BEGIN TRANSACTION ISOLATION LEVEL READ COMMITTED
  - SELECT * FROM wallets WHERE id IN (from, to) ORDER BY id FOR UPDATE
  - Validate balances and status
  - INSERT ledger entries (DEBIT from, CREDIT to)
  - UPDATE wallet balances
  - COMMIT
  - Retry on serialization failure (3x with exponential backoff)

      "dropoff_lat": -6.2950,
      "dropoff_lng": 106.8638,
      "distance_km": 12.5,

        "base_fare": 10000,

        "total": 60000
      },

      "status_updated_at": "2026-08-14T10:30:00Z",

     - base_fare: Rp 10,000
     - distance_charge: distance_km * 4,000
     - total = base_fare + distance_charge
  
  2. Deduct escrow from wallet (DEBIT):
     - Reference: RIDE_ESCROW
     - Destination: SYSTEM_ESCROW wallet
  
  3. Create ride_orders table row:
     - Status: CREATED
     - Then update to SEARCHING_DRIVER (separate update)
     - Order expires in 15 minutes if no driver assigned
  
  4. Trigger driver matching (async):
     - Query available drivers within 5km (earthdistance)
     - Filter: is_online=TRUE, working_status='IDLE', status='ACTIVE'
     - Check min_balance_threshold <= driver_wallet.balance

  - COMMIT
  
  Race Condition Handling (Bug #1):
  - If another driver concurrently accepts → lock timeout/conflict
  - First to acquire lock succeeds, second gets 409 CONFLICT
  - No "double assignment" possible

7.3 UPDATE RIDE STATUS
────────────────────────────────────────────────────────────────────────────────

PATCH /rides/{order_id}/status
  Auth: Required (user_type: customer or driver)
  Role: Customer (owns order) or Driver (assigned to order)
  Rate Limit: 60 req/min per user
  
  Request:
  {
    "status": "DRIVER_ARRIVED" | "TRIP_STARTED" | "COMPLETED" | "CANCELLED"
  }
  
  Valid Status Transitions (STATE MACHINE — DATABASE_SCHEMA, LOGIC_FLOW 2.1):
  CREATED → SEARCHING_DRIVER → DRIVER_ASSIGNED → DRIVER_ARRIVED → 
    TRIP_STARTED → COMPLETED → SETTLED
  
  Cancellations:
  - Before DRIVER_ASSIGNED: Full refund to customer (no fee)
  - After DRIVER_ASSIGNED: Rp 5,000 cancellation fee to driver
  - After DRIVER_ARRIVED: Rp 10,000 cancellation fee to driver
  
  Response: 200 OK
  {
    "success": true,
    "data": {
      "order_id": "uuid-ride-order-123",
      "status": "DRIVER_ARRIVED",
      "status_updated_at": "2026-08-14T10:32:00Z"
    }
  }
  
  Errors:
  - 400 INVALID_REQUEST: Invalid status value
  - 401 UNAUTHORIZED: Invalid token
  - 403 FORBIDDEN: User not allowed to update this order
  - 404 NOT_FOUND: Order doesn't exist
  - 409 CONFLICT: Invalid state transition
  
  Settlement (COMPLETED → SETTLED):
  - Triggered automatically when status = COMPLETED
  - If payment_method = WALLET:
    * CREDIT driver wallet: ride_orders.driver_earning
    * DEBIT escrow: ride_orders.estimated_fare
    * Platform deduction: 20% of estimated_fare
    * Driver receives: 80% of fare

    * Item not available (available = false)
    * Insufficient wallet balance
    * Option selection mismatch (missing required option)
    * Menu versioning conflict (HALAMAN v2.0-FIXED #4)

Business Logic:
  1. Validate merchant status = ACTIVE (not PENDING_VERIFICATION)
  2. Validate all items available = true
  3. Validate customer wallet balance >= total_amount
  4. Create food_orders row (status = CREATED)
  5. Create food_order_items rows (one per item)
  6. Deduct escrow from customer wallet:
     - DEBIT: customer wallet
     - CREDIT: SYSTEM_ESCROW
     - reference_type: FOOD_ESCROW
  7. Update order status to CONFIRMED (automatic)
  8. Notify merchant via websocket/long-polling

State Transitions (FOOD_ORDER_STATUS_ENUM from DATABASE_SCHEMA):
CREATED → CONFIRMED → PREPARING → READY_FOR_PICKUP → 
  PICKED_UP → IN_TRANSIT → DELIVERED → SETTLED

8.4 UPDATE FOOD ORDER STATUS
────────────────────────────────────────────────────────────────────────────────

PATCH /food-orders/{order_id}/status
  Auth: Required (merchant or driver on order)
  
  Request:
  {
    "status": "PREPARING" | "READY_FOR_PICKUP" | "PICKED_UP" | "IN_TRANSIT" | "DELIVERED" | "CANCELLED"
  }
  
  Response: 200 OK (same structure as create)
  
  Status Update Rules:
  - CONFIRMED → PREPARING: Merchant only (order accepted)
  - PREPARING → READY_FOR_PICKUP: Merchant (food prepared)
  - READY_FOR_PICKUP → PICKED_UP: Driver (picked up from merchant)
  - PICKED_UP → IN_TRANSIT: Driver
  - IN_TRANSIT → DELIVERED: Driver
  - DELIVERED → SETTLED: Automatic (trigger-based) or Manual (admin)
  
  Cancellation:
  - Before CONFIRMED: Full refund
  - After CONFIRMED: Rp 5,000 fee to merchant
  - After READY_FOR_PICKUP: Rp 10,000 fee to merchant
  
  Settlement (DELIVERED → SETTLED) — (LOGIC_FLOW 3.4, PRD G-Food)
  - Merchant earning: 80% of (subtotal + delivery_fee) - commission
  - Driver earning: Delivery fee (from G-Food delivery)
  - Platform cut: 20% of subtotal
  - Ledger entries:
    * DEBIT: SYSTEM_ESCROW (escrow amount)
    * CREDIT: merchant wallet (merchant earning)
    * CREDIT: driver wallet (driver earning)
    * CREDIT: SYSTEM_PLATFORM (platform cut)
