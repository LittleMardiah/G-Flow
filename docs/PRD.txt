📋 EXECUTIVE SUMMARY
================================================================================

PROBLEM STATEMENT

Layanan transportasi, pesan-antar makanan, dan kurir instan saat ini terfragmentasi
dengan sistem pembayaran yang tidak efisien. Setiap layanan menggunakan dompet
digital terpisah, menyebabkan:
- Race condition saat multiple driver menerima order bersamaan
- Double spending pada wallet payment (pengeluaran ganda)
- State drift (ketidaksesuaian status order antara client & server)
- Concurrency bugs saat high-volume transaction di infrastructure terbatas
- Tidak ada unified ledger untuk audit keuangan yang akurat

SOLUTION OVERVIEW

G-Flow adalah platform super-app terpadu berbasis Modular Monolith Golang yang
mengintegrasikan 4 modul core + 1 mobile app dalam satu ekosistem:

1. PayPulse — Digital wallet engine dengan double-entry bookkeeping ledger
2. G-Ride — Ride-hailing dengan driver dispatch matching & pessimistic locking
3. G-Food — Food delivery dengan merchant catalog & order management
4. G-Send — Instant logistics untuk package delivery
5. Mobile App — Flutter/React Native untuk Customer, Driver, & Merchant

Infrastruktur: Supabase PostgreSQL + Golang backend native + Mobile App

VALUE PROPOSITION

- Financial Accuracy: Zero balance discrepancy via double-entry bookkeeping
- Zero Race Conditions: Formal state machines + SELECT FOR UPDATE locking
- Free Tier Ready: Berjalan di Supabase Free Tier + Render.com (No CC required)
- Single Codebase: Maintainable untuk solo developer dengan structured modularity
- Complete Ecosystem: Customer, Driver, Merchant, Admin dalam 1 platform utuh

TARGET USERS

| Role      | Goals                                                                 |
|-----------|-----------------------------------------------------------------------|
| Customer  | Memesan ride/food/package, manage PayPulse balance, track order       |
| Driver    | Accept orders, update location, complete delivery, withdraw earnings  |
| Merchant  | Manage menu catalog, accept/prepare orders, track sales & revenue     |
| Admin     | Monitor ledger audit trail, manage disputes, suspend/freeze accounts  |

F002: Double-Entry Bookkeeping Ledger
────────────────────────────────────────────────────────────────────────────────

DESCRIPTION: Financial backbone. Setiap mutation menciptakan 2 balanced entries.

LEDGER ENTRY SCHEMA:
  - id: UUID PRIMARY KEY
  - wallet_id: UUID (FK to wallets)
  - type: 'DEBIT' | 'CREDIT'
  - amount: NUMERIC(15,2)
  - reference_type: 'WALLET_TOPUP' | 'RIDE_PAYMENT' | 'FOOD_DELIVERY' | 'SEND_DELIVERY' | 'ORDER_REFUND' | 'PLATFORM_FEE' | 'DRIVER_EARNING'
  - reference_id: UUID (link ke order_id atau transaction_id)
  - description: TEXT
  - created_at: TIMESTAMP

INVARIANT: SUM(amount) WHERE type='DEBIT' = SUM(amount) WHERE type='CREDIT'

ATOMIC TRANSFER PROCESS:
  BEGIN TRANSACTION;
    1. SELECT balance FROM wallets WHERE id = from_wallet FOR UPDATE;
    2. IF balance < amount THEN ROLLBACK; RETURN error;
    3. UPDATE wallets SET balance = balance - amount WHERE id = from_wallet;
    4. INSERT ledger_entries VALUES (debit_entry, from_wallet, DEBIT, ...);
    5. INSERT ledger_entries VALUES (credit_entry, to_wallet, CREDIT, ...);
    6. UPDATE wallets SET balance = balance + amount WHERE id = to_wallet;
  COMMIT;

VALIDATION RULES:
  - ✅ Setiap transaction = 1 debit + 1 credit
  - ✅ Amounts harus exactly balance
  - ✅ No partial transactions (atomicity)
  - ✅ All transactions immutable (no delete/update ledger entries)


F003: Transfer + Top-Up + Idempotency Layer
────────────────────────────────────────────────────────────────────────────────

DESCRIPTION: User dapat transfer antar wallet dengan guarantee no duplicate charge.

INPUTS (TRANSFER):
  POST /wallets/transfer
  {
    "from_wallet_id": "uuid",
    "to_wallet_id": "uuid",
    "amount": 50000,
    "description": "Payment for ride XYZ"
  }
  Headers: X-Idempotency-Key: uuid (REQUIRED), Authorization: Bearer {token}

INPUTS (TOP-UP):
  POST /wallets/topup
  {
    "amount": 100000,
    "method": "simulated"  // Internal simulation, not real payment
  }
  Headers: X-Idempotency-Key: uuid (REQUIRED), Authorization: Bearer {token}

IDEMPOTENCY IMPLEMENTATION:
  - Cek cache SELECT FROM idempotency_cache WHERE key = $1
  - If found & not expired → return cached response
  - If found & expired → delete & continue
  - Execute transfer/topup
  - Cache result with TTL 24 hours
  - Return response

EDGE CASES:
  - Insufficient balance → 422 Unprocessable Entity
  - Invalid wallet ID → 404 Not Found
  - Duplicate request (same key) → 200 OK + cached response
  - Transfer to self → 400 Bad Request

F005: G-Ride Driver Dispatch Matching Engine (CRITICAL — RACE CONDITION PREVENTION)
────────────────────────────────────────────────────────────────────────────────

DESCRIPTION: Thread-safe driver matching engine untuk prevent race condition.

ORDER STATE MACHINE:
  [CREATED] → [SEARCHING_DRIVER] → [DRIVER_ASSIGNED] → [DRIVER_ARRIVED] → [TRIP_STARTED] → [COMPLETED] → [SETTLED]
                           ↑                              ↓
                     [CANCELLED] (before assign)    [CANCELLED] (after assign with penalty)

INPUTS:
  POST /rides/orders/{order_id}/accept
  {
    "driver_id": "uuid"
  }
  Headers: Authorization: Bearer {token}

PROCESS (ATOMIC — WITH PESSIMISTIC LOCKING):
  BEGIN TRANSACTION;
    SET LOCAL statement_timeout = '3000ms';  -- Prevent hanging connections
    1. SELECT status, assigned_driver FROM ride_orders WHERE id = $order_id FOR UPDATE;
    2. IF status != 'SEARCHING_DRIVER' THEN
         ROLLBACK;
         RETURN HTTP 409 "Order no longer available"
    3. UPDATE ride_orders SET status = 'DRIVER_ASSIGNED', assigned_driver_id = $driver_id, assigned_at = NOW() WHERE id = $order_id;
    4. INSERT INTO audit_trail (order_id, from_status, to_status, actor_id, timestamp) VALUES (...);
  COMMIT;

CONCURRENCY TEST SCENARIO:
  Time 0ms: Driver A clicks Accept
  Time 1ms: Driver B clicks Accept (concurrent)
  Time 2ms: Driver C clicks Accept (concurrent)

  Outcome:
  - Driver A: Acquires lock first → HTTP 200 "ASSIGNED" ✅
  - Driver B: Lock wait → after A commits, fails check → HTTP 409
  - Driver C: Same as B → HTTP 409

  Result: ONLY 1 driver assigned. ZERO double-booking. ✅

OUTPUTS:
  {
    "order_id": "uuid",
    "status": "DRIVER_ASSIGNED",
    "driver_id": "uuid",
    "customer_id": "uuid",
    "pickup": { "lat": -6.123, "lng": 106.456 },
    "dropoff": { "lat": -6.234, "lng": 106.567 },
    "estimated_fare": 35000,
    "assigned_at": "ISO-8601"
  }

MIDDLEWARE:
  func AuthMiddleware(c *gin.Context) {
    token := c.GetHeader("Authorization")
    claims := validateJWT(token)
    if claims == nil {
      c.JSON(401, "Unauthorized")
      return
    }
    c.Set("user_id", claims.Sub)
    c.Set("user_type", claims.UserType)
    c.Set("wallet_id", claims.WalletId)
    c.Next()
  }

  func RequireRole(requiredRoles ...string) gin.HandlerFunc {
    return func(c *gin.Context) {
      userType := c.GetString("user_type")
      for _, role := range requiredRoles {
        if userType == role { c.Next(); return }
      }
      c.JSON(403, "Forbidden")
    }
  }
