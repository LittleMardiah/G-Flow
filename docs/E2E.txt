## 1. Tujuan & Prinsip

1.1. Single source of truth untuk End-to-End testing G-Flow. Dokumen ini menjawab:
     test apa yang dijalankan, tools apa, data apa, dan bagaimana integrasinya ke CI.

1.2. Prinsip yang dipegang:
     - Quality > Speed: tiap journey harus SLA-valid (ledger balanced, no double spend,
       refund akurat) — bukan sekadar smoke test.
     - Zero Risk: tidak pernah menyentuh production; environment E2E terisolasi penuh
       (DB + Redis khusus, data seed anonim).
     - Free / OSS: hanya tool gratis (Playwright, Flutter integration_test, ffmpeg,
       GitHub Actions) — tanpa cloud test farm berbayar.
     - Visual evidence: tiap flow menghasilkan video + screenshot sebagai bukti.

1.3. Ini level system/E2E di piramida testing. Detail unit/integration (TC-001 s/d
     TC-012, TC-015 s/d TC-018 dari STP) BUKAN bagian dari scope ini — dipakai hanya
     sebagai precondition invariant (lihat section 9.5).

1.4. Level E2E di scope ini mengikuti 6 user journey Level-4 yang sudah didefinisikan STP:
     Customer (book ride / order food), Driver (accept / complete), Merchant (accept /
     prepare), Admin (view ledger / suspend user), + polling state sync (TC-013) &
     background reconciliation (TC-014).

Alternatif yang DIKURANGI dan kenapa tidak dipilih:
- Cypress untuk web: lebih berat, arsitektur runners lebih mahal di CI, ekosistem video
  sudah bawaan tapi built -in test-ing mahal. Playwright lebih ringan satu job.
- WDIO/WebdriverIO: overkill untuk 2 Next.js app.
- Appium untuk mobile: perlu appium server + XML-tree (brutal untuk Flutter yang pakai
  render sendiri), lambat, banyak flake. Tidak dipilih.
- Maestro untuk mobile: ringan & mudah baca, tapi akses ke widget tree Flutter lebih
  terbatas dan integrasi ke CI (emulator provisioning) tidak sematang integration_test.
  Dipilih integration_test demi determinisme.

### 2.2. Backend Strategy (GitHub Actions service containers)

REKOMENDASI UTAMA — service containers native di workflow `e2e.yml`:
```yaml
services:
  postgres:
    image: postgres:15-alpine   # menyesuaikan versi prod; repo punya docker-compose postgres:15
  redis:
    image: redis:7-alpine
```
- Job backend menjalankan: `go run ./cmd/api` (atau build binary) + migrasi
  `migrations/*.up.sql` + seed E2E.
- Alasan: nol biaya, terisolasi per run, deterministik versi. Sesuai docker-compose.yml
  yang sudah ada (postgres:15-alpine, redis:7-alpine) tapi di CI pakai PG image yang
  selaras dengan prod ([PERLU VERIFIKASI] versi Postgres produksi: STP menyebut PG 15).
- Trade-off vs alternatif:
  - Alternatif A (testcontainers-go di dalam job Go): cocok untuk integration test,
    tapi buat E2E malah menambah compile layer dan tidak reusable untuk Playwright.
  - Alternatif B (docker-compose.yml dipanggil di CI): komposisi benar, tapi service
    containers GH Actions lebih singkat dan tidak perlu daemon docker manual.

### 2.3. Flutter setup yang HARUS dilakukan (belum ada di repo — terverifikasi)
- Tambah `integration_test: {sdk: flutter}` + sudah ada `flutter_test` di 3 pubspec.
- Folder `integration_test/` per app (belum ada).
- Build/gate: `flutter test integration_test -d <device>` di CI (Android emulator
  container; lokal: `adb` atau desktop Linux runner dengan embedder).

### 2.4. Video + Screenshot Strategy
- Web (Playwright): otomatis — `video: 'on-first-retry'` atau `'retain-on-failure'`,
  `trace: 'retain-on-failure'`, `screenshot: 'only-on-failure'`, plus `page.screenshot()`
  eksplisit tiap milestone journey untuk evidence.
- Mobile (Flutter): `binding.takeScreenshot()` di tiap milestone; untuk video penuh pakai
  `adb exec-out screenrecord` (Android emulator). Fallback offline: kumpulkan screenshots
  per step → ffmpeg -framerate 1 stitch → mp4/webm, gratis.

### 2.5. CI Integration (ringkasan — detail di section 8)
- Workflow terpisah `e2e.yml`, `workflow_dispatch` + path filter, jalankan backend+
  PG+Redis sebagai service, matrix per-app, upload artifact (video, screenshot, HTML
  report), retry hanya untuk job mobile yang rawan flake.

## 4. Cross-App Journey Test (INTI E2E)

> Memakai 2-3 app sekaligus; backend + ledger sebagai orakel kebenaran.
> Setiap journey DIVALIDASI dengan invariant: SUM(debit)=SUM(credit), tidak ada
> double-spend, refund akurat, status tidak ghost-state.

| ID | Journey | Mini Steps | Oracle (yang divalidasi) | Priority |
|----|---------|------------|--------------------------|----------|
| J1: | Ride Journey | Customer top-up → book ride → driver ONLINE accept → driver PATCH ARRIVED/STARTED/COMPLETED → customer rate → settlement auto | Escrow = 0 setelah SETTLED; driver +80%, platform +20%; refund surplus/shortfall benar; 2 ledger entri per leg | P0 |
| J2: | Food Journey | Customer order (PayPulse) → merchant CONFIRM→PREPARING→READY_FOR_PICKUP → driver PICKED_UP→IN_TRANSIT→DELIVERED → 4-way settlement | customer −(items+delivery−voucher), merchant +(85% items), driver +(delivery−10%), platform +(15% items + 10% delivery); escrow balanced; porsi voucher → SYSTEM_PROMO_SUBSIDY | P0 |
| J3: | Send Journey (multi-stop + RTS) | Customer create 3-stop send → driver accept → 1 stop delivered, 1 skipped → RETURN_REQUIRED → RETURNED_TO_SENDER → 3-way settlement | Driver dapat allocated_fare untuk stop delivered + RTS fee; refund porsi skipped ke customer (cash case: DEBIT driver / CREDIT customer); ledger balanced | P1 |
| J4: | Wallet Flow | Register customer → top-up → transfer P2P (idempotent) → driver/merchant withdraw → admin approve → cek balans akhir | P2P 1 ledger DEBIT/CREDIT; topup idempotent (retry tak dobel); withdraw COMPLETED setelah approve; kirim ke wallet non-ACTIVE gagal | P0 |
| J5: | Admin Reversal | Pilih transaksi settle → [PERLU VERIFIKASI] mekanisme 2FA admin → reverse via `POST /admin/ledger/{id}/reverse` → cek ledger | DEBIT↔CREDIT dibalik; `is_reversed=TRUE`; SUM tetap balanced; saldo user kembali | P1 |
| J6: | Ledger Reconciliation pasca-semua-journey | Jalankan J1-J5 lalu `GET /ledger/audit` | `balance_check: "BALANCED"`; selisih Rp 0; skenario double-spend tidak pernah terjadi (0 occurrences) | P1 |

## 6. Prioritization (Tier)

### TIER 1 (P0 — WAJIB): 25 test
AD-01, AD-02, AD-03, AD-06, AD-07 | CU-02, CU-03, CU-04, CU-05 | DR-01, DR-02, DR-03, DR-05 |

### TIER 2 (P1 — PENTING): 26 test
LP-01, LP-05, LP-06 | AD-05, AD-08, AD-09 | CU-01, CU-06, CU-08, CU-09, CU-10 |
DR-04, DR-06, DR-07 | ME-04, ME-05, ME-06 | J3, J5, J6 | N-07, N-08, N-09, N-11, N-12, N-14

### TIER 3 (P2 — BONUS): 8 test
LP-02, LP-03, LP-04 | AD-04 | CU-07 | ME-07 | N-10, N-13

### Justifikasi
- TIER 1 = core revenue flow + invariants keuangan (ledger, double-spend, idempotency,
  refund). Ini yang menentukan "G-Flow bisa rilis atau tidak" per acceptance criteria PRD
  (double spending 0, ledger discrepancy Rp 0, idempotency 100%).
- TIER 2 = supporting UX & level-2 flows (multi-stop, RTS, review, documents) — penting
  untuk kepuasan dan kepatuhan (KYC, dokumen) tapi tidak memblokir rilis inti.
- TIER 3 = polish & edge (responsive, export, menu version modal, rate-limit).
  Dimasukkan hanya jika kuota CI/repo waktu tersedia.
- Tidak semua UI di-cover: E2E level di atas cukup untuk 1-2 critical journey per fitur,
  sesuai rekomendasi STP (10-15% usaha di level E2E).

## 8. CI Integration Plan

### 8.1. Workflow baru: `e2e.yml`
```yaml
name: e2e
on:
  workflow_dispatch:            # manual trigger tetap mungkin
  push:
    paths: ['backend/**','apps/**','migrations/**','docs/E2E.txt']
  pull_request:
    paths: ['backend/**','apps/**','migrations/**']
```
- Path filter hemat minutes: journey & negative hanya berjalan saat ada perubahan yang
  memaksa E2E, bukan di tiap commit acak.
- Note: admin_web sampai saat ini TIDAK punya job di `ci.yml` (terverifikasi) — E2E web
  harus inline-cover `apps/admin_web/**` agar ada pengawal kualitas.

### 8.2. Job structure
| Job | Matrix | Service container | Isi |
|-----|--------|-------------------|-----|
| `e2e-setup` | - | postgres:15 + redis:7 | Migrate + seed + start backend (`go run ./cmd/api` / build), expose health port, keluarkan base URL (env var `BASE_URL`) |
| `e2e-web` | landing_page / admin_web | - (pakai base URL dari setup) | `npx playwright test` per project; upload hasil |
| `e2e-mobile-customer` / `-driver` / `-merchant` | per-app | - | Android emulator container + `flutter test integration_test`; pakai backend yang sama |
| `e2e-server-journeys` | - | - | Jalankan J1-J6 sebagai kode uji (Playwright web API helpers + Flutter) |
| `e2e-gate` | - | - | Fail jika salah satu job E2E gagal (pakai rule: TIDAK `continue-on-error` di sini, tidak seperti `flutter` di ci.yml) |

### 8.3. Artifact upload
- `actions/upload-artifact` per job:
  - web: `playwright-report/`, `test-results/*.mp4`, `*.trace.zip`
  - mobile: `integration_test/screenshots/**`, video `screenrecord`/ffmpeg output
  - server: `test-output.log` + coverage jika ada
- Retention 14 hari; naming `e2e-${{github.run_id}}-<app>`.

### 8.4. Retry strategy
- `e2e-mobile-*`: `max-attempts: 2` (mobile emulator rawan flake cold-start).
- Playwright: `retries: 1` di config, `video: 'on-first-retry'`.
- Flutter test: jalankan ulang test yang `flaky` maks 1x sebelum ditandai fail
  (pakai tag `@flaky` eksplisit di nama test).

### 8.5. Konvensi non-negosiable di E2E CI
- Never `continue-on-error: true` untuk job E2E.
- Semua job butuh `e2e-setup` selesai & health `/ready` 200.
- Durasi target per job: web < 15 mnt, mobile < 40 mnt, journeys < 20 mnt.

  disini itu keputusan benar untuk unit/integration, tapi E2E wajib real).

### 9.4. Tool & process Saran
- Playwright tetap rekomendasi #1; kalau butuh parallel ringan bisa `npx playwright
  test --workers=2`. Jangan pindah ke Cypress.
- Untuk mobile, alternative layak: `patrol` (tool E2E Flutter; tambah app-side dep) —
  tapi pilih integration_test dulu karena sudah SDK resmi & tanpa biaya.
- Tambahkan "fixture helper HTTP" yang memakai API backend (Gin) untuk setup data
  (topup, order) sebelum test UI — jadi test tidak menunggu waktu webhook natural. [USULAN]
- Pertimbangkan memakai k6 di job `e2e-server-journeys` jika ingin verify beban — tapi
  k6 lebih cocok untuk load test (sudah standar repo), bukan E2E fungsional.

### 9.5. Risiko yang perlu dimitigasi
- Flake mobile cold-start → retry 1x sudah aman, tapi pastikan artifact video tersimpan
  di failure untuk diagnosa.
- Rate limit (wallet/order ops 10/min; driver accept 30/min) bisa menjebol test yang
  banyak call API — desain test roomy (≤ 8 call ops wallet per test).
- Menjalankan `flutter test integration_test` butuh device; pastikan job matrix tidak
  menghabiskan konteks (Android emulator berbagi memory) — jalankan driver & merchant
  urutan sesudah customer bila memory dibatasi.
- Test yang menunggu webhook (topup) harus punya timeout path late-settlement 60s,
  jangan hardcode sleep (mirror `is_late_settlement`).
- Karena admin_web belum terjaga lint/build di CI, jangan taruh asistensi ganda:
  E2E web admin BISA gagal di hal semantik runtime yang seharusnya ketahuan di build —
  saran: naikkan CI coverage admin_web di fase selanjutnya.

- (a) Yang mungkin terlewat: tidak ada test untuk "Voucher + cancel (+refund)" interplay
