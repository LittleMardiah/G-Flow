### 3.2 Severity Levels Definition

**CRITICAL** (RTO: < 1 hour, RPO: 0 data loss)
- Primary database complete failure / data corruption
- Ledger entries inconsistency (SUM DEBIT ≠ SUM CREDIT)
- Race condition causing double-spending
- Data breach (customer PII exposed)
- Authentication system unavailable
- All user balances incorrect

**HIGH** (RTO: 2-4 hours, RPO: ≤ 5 minutes)
- Backend service crash (recoverable)
- Redis down (cache layer, fallback available)
- Read replica failure (if applicable)
- API response time degradation (> 5s)
- Partial data corruption (one table)

**MEDIUM** (RTO: 4-24 hours, RPO: ≤ 1 hour)
- Admin portal unavailable (non-customer-facing)
- Analytics service down
- Non-critical microservice failure
- Configuration management issues

**LOW** (RTO: > 24 hours, RPO: ≤ 1 day)
- Development/staging environment down
- Documentation unavailable
- Cosmetic UI issues

4. BACKUP & REDUNDANCY STRATEGY
================================================================================

### 4.1 Backup Architecture

#### 4.1.1 Database Backups (Supabase PostgreSQL)

```
Strategy: Automated Snapshots (Primary) + Manual Backup (Secondary)

Frequency:
  - Automatic: Hourly (Supabase native)
  - Manual: Daily (developer initiated, CLI)
  - Point-in-time: 7-day restore window (Supabase Pro feature)

Retention:
  - Automatic: 7 days (Supabase default)
  - Manual: 30 days (developer responsibility)

Storage:
  - Primary: Supabase managed storage (AWS S3)
  - Secondary: Developer GitHub repo (schema DDL only, not data)
  - Backup Verification: Weekly restore test (staging environment)

RPO: 5 minutes (hourly snapshots guarantee no more than 1 hour loss)
RTO: 15 minutes (restore from snapshot)
```

**Backup Implementation:**

```bash
# Automatic (Supabase handles):
- Hourly snapshots via Supabase dashboard
- Retention: 7 days (rolling)

# Manual Backup (Daily):
pg_dump -h db.supabase.co -U postgres -d g_flow_prod > backup_$(date +%Y%m%d).sql

# Point-in-Time Recovery (within 7 days):
- Via Supabase dashboard: Create backup from timestamp
- Or CLI: supabase db push --db-url postgresql://...

# Restore Procedure:
psql -h restore-instance.supabase.co -U postgres -d g_flow_restored < backup_20260814.sql
```

#### 4.1.2 Application & Code Backups

```
Version Control: GitHub (public repo — no secrets)
  - Repository: https://github.com/[user]/g-flow-backend
  - Backup Frequency: Real-time (every git push)
  - Mirror: GitHub native redundancy (3 geographies)

Configuration Files:
  - Backend config: Render environment variables (backed up via docs)
  - Database schema: DATABASE_SCHEMA.sql (version-controlled in Git)
  - API contract: API_CONTRACT.md (version-controlled in Git)

Secrets Management:
  - DATABASE_URL: Render Secret (encrypted)
  - REDIS_URL: Render Secret (encrypted)
  - JWT_SECRET: Render Secret (encrypted)
  - Backup: Encrypted vault (developer local only, never committed)

Recovery: Clone from GitHub + set Render environment vars
```

#### 4.1.3 Ledger Entries Backup (Immutable)

```
Strategy: Continuous Archival (Postgres native)

Frequency: Real-time (every transaction)
  - Ledger entries appended only (INSERT, never UPDATE except is_reversed)
  - is_reversed flag immutable after reversal

Retention:
  - Active ledger: Indefinitely in main table
  - Archive: 90-day snapshot dump (for audit trail)

Verification: Nightly job
  SELECT SUM(amount) FROM ledger_entries WHERE entry_type='DEBIT' as debit,
         SUM(amount) FROM ledger_entries WHERE entry_type='CREDIT' as credit;
  IF debit != credit THEN ALERT "Ledger Imbalance"

Recovery: Immutable ledger = no recovery needed (integrity guaranteed)
```

### 4.2 Redundancy & High Availability

| Component | Redundancy Type | Implementation | Failover Time |
|-----------|-----------------|-----------------|---------------|
| Database | Single (Auto-failover via Supabase) | Primary + automated backups | 15 min |
| Application | Single (No multi-region V1.0) | Graceful restart on crash | 5 min |
| Redis Cache | Single (Optional failover via Upstash) | Managed service + AOF persistence | 2 min |
| API Health Check | Auto-restart on failure | Render health check + restart policy | 30 sec |
| DNS | Render native | Automatic IP routing | Instant |

**Failover Mechanisms:**

1. **Database Failover (Supabase):**
   - Supabase manages replication (async)
   - On primary failure: Failover to replica (automatic)
   - RTO: 15 minutes
   - Data loss: ≤ 5 minutes (RPO)

2. **Application Failover (Render):**
   - Health check: GET /health every 60s
   - On failure: Automatic container restart
   - RTO: 2 minutes (cold start)
   - Stateless → no data loss

3. **Redis Failover (Upstash):**
   - Managed service (provider handles failover)
   - AOF persistence enabled
   - RTO: < 2 minutes
   - Data loss: Minimal (persisted to disk)

4. **DNS Failover (Manual):**
   - If Render completely down:
     * Change DNS A record to backup IP
     * Or switch to GitHub Pages static fallback
   - RTO: 10 minutes (DNS TTL 300s + propagation)

### 5.1 SCENARIO 1: DATABASE COMPLETE FAILURE / CORRUPTION

**Severity**: CRITICAL | **RTO**: 1 hour | **RPO**: 5 minutes

**Symptoms / Detection:**
- Alert: Database connection refused (pgx timeout)
- Monitoring: /health endpoint returns database error
- Threshold: No successful queries for 30 seconds

**Impact Assessment:**
- Affected Systems: All (wallet, rides, food, send, auth)
- User Impact: Complete service unavailability
- Business Impact: Revenue loss, user trust damage, SLA breach

**Immediate Actions (First 15 minutes):**
1. **Acknowledge Alert:**
   - PagerDuty/Slack alert fired
   - Incident Commander opens incident ticket
   - Severity: P0 (all hands)

2. **Confirm Issue:**
   ```bash
   # Test database connectivity
   psql -h db.supabase.co -U postgres -c "SELECT 1"
   
   # Check Supabase status dashboard
   # https://supabase-status.com
   
   # Verify error in application logs
   # Render dashboard → Logs tab
   ```

3. **Notify Team:**
   - Post to #incidents Slack channel
   - Message: "P0 Database Failure - Starting recovery"

**Recovery Steps:**

1. **Preparation Phase (5 minutes):**
   - [ ] Verify backup integrity (most recent snapshot)
   - [ ] Check Supabase restore point (within 7 days)
   - [ ] Stop application servers (Render)
   - [ ] Allocate new database instance (if needed)

2. **Execution Phase (15 minutes):**
   
   ```bash
   # Step 1: Identify latest backup
   # Via Supabase dashboard:
   # Settings → Backups → List (select hourly snapshot)
   
   # Step 2: Create new restore instance
   supabase db restore --backup-id <backup-id> --restore-to <new-db-instance>
   
   # Step 3: Validate restore
   psql -h <new-instance>.supabase.co -U postgres -d g_flow \
     -c "SELECT COUNT(*) FROM ledger_entries"
   
   # Step 4: Verify ledger balance
   psql -h <new-instance>.supabase.co -U postgres -d g_flow << EOF
   SELECT
     SUM(CASE WHEN entry_type='DEBIT' THEN amount ELSE 0 END) as total_debit,
     SUM(CASE WHEN entry_type='CREDIT' THEN amount ELSE 0 END) as total_credit
   FROM ledger_entries;
   EOF
   
   # Step 5: Update APPLICATION connection string
   # Via Render dashboard: Environment → DATABASE_URL
   # Set to: postgresql://user:pass@<new-instance>.supabase.co/g_flow
   
   # Step 6: Restart application
   # Via Render dashboard: Deploy → Restart
   ```

3. **Validation Phase (10 minutes):**
   - [ ] /health endpoint returns 200 OK
   - [ ] GET /wallets/{id}/balance returns correct balance
   - [ ] Verify ledger (sum debit = sum credit)
   - [ ] Run smoke tests (login, book order, create wallet)
   - [ ] Monitor error rate < 0.1%

4. **Post-Recovery:**
   - [ ] Verify data integrity (row counts match backup)
   - [ ] Check recent transactions (last 10 orders)
   - [ ] Monitor metrics for 30 minutes (latency, errors)
   - [ ] Notify customers (if > 1 hour downtime)
   - [ ] Document incident in #incidents
   - [ ] RCA due within 24 hours

**Rollback Plan:**
- Condition: Restored database has data corruption
- Action: Restore from earlier backup (7-day window)
- Impact: Data loss ≤ 1 hour

**Expected RTO**: 1 hour | **Expected RPO**: 5 minutes

### 5.2 SCENARIO 2: LEDGER IMBALANCE DETECTED (SUM DEBIT ≠ SUM CREDIT)

**Severity**: CRITICAL | **RTO**: 30 minutes | **RPO**: 0 minutes

**Symptoms / Detection:**
- Alert: Nightly ledger verification job fails
- Error: "Ledger imbalance detected: debit=X, credit=Y"
- Monitoring: Audit trail inconsistency
- Threshold: Any discrepancy > Rp 0

**Impact Assessment:**
- Affected Systems: Financial ledger (all transactions)
- User Impact: Wallet balances potentially incorrect
- Business Impact: Audit failure, regulatory breach, loss of customer trust

**Immediate Actions (First 15 minutes):**
1. Incident Commander notified
2. Check error logs for root cause
3. Query ledger_entries for orphaned entries
4. Freeze account modifications (stop accepting orders) — optional

**Recovery Steps:**

1. **Diagnosis (10 minutes):**
   
   ```sql
   -- Query 1: Identify imbalance
   SELECT
     (SELECT SUM(amount) FROM ledger_entries WHERE entry_type='DEBIT') as total_debit,
     (SELECT SUM(amount) FROM ledger_entries WHERE entry_type='CREDIT') as total_credit,
     (SELECT SUM(amount) FROM ledger_entries WHERE entry_type='DEBIT') -
     (SELECT SUM(amount) FROM ledger_entries WHERE entry_type='CREDIT') as difference;
   
   -- Query 2: Find orphaned DEBIT entries (no matching CREDIT)
   SELECT * FROM ledger_entries
   WHERE entry_type='DEBIT'
   AND reference_id NOT IN (
     SELECT reference_id FROM ledger_entries WHERE entry_type='CREDIT'
   );
   
   -- Query 3: Find orphaned CREDIT entries
   SELECT * FROM ledger_entries
   WHERE entry_type='CREDIT'
   AND reference_id NOT IN (
     SELECT reference_id FROM ledger_entries WHERE entry_type='DEBIT'
   );
   
   -- Query 4: Check for duplicate entries
   SELECT reference_id, entry_type, COUNT(*) as count
   FROM ledger_entries
   GROUP BY reference_id, entry_type
   HAVING COUNT(*) > 1;
   ```

2. **Identify Root Cause:**
   - Missing ledger entry (incomplete transaction)
   - Duplicate entry (idempotency cache missed)
   - Corrupted data (manual database edit)
   - Bug in settlement trigger (check recent deployments)

3. **Execution Phase (15 minutes):**

   **Case A: Missing CREDIT entry**
   ```sql
   -- Insert missing CREDIT
   INSERT INTO ledger_entries (
     wallet_id, entry_type, amount, reference_type, reference_id, created_at
   ) VALUES (
     'uuid-wallet-123', 'CREDIT', 500000, 'RIDE_SETTLEMENT', 'order-id-456', NOW()
   );
   ```

   **Case B: Duplicate entry (remove)**
   ```sql
   -- Soft delete (mark as reversed)
   UPDATE ledger_entries
   SET is_reversed = TRUE
   WHERE id = 'uuid-duplicate-entry'
   AND entry_type = 'CREDIT';
   ```

   **Case C: Transaction in wrong direction**
   ```sql
   -- Create reversal entry
   INSERT INTO ledger_entries (
     wallet_id, entry_type, amount, reference_type, reference_id, is_reversed
   ) VALUES (
     'uuid-wallet-123', 'DEBIT', 500000, 'CORRECTION', 'ref-123', FALSE
   );
   ```

4. **Validation Phase (5 minutes):**
   - [ ] Rerun ledger balance query (must equal 0)
   - [ ] Verify affected wallets (balance_after correct)
   - [ ] Check transaction receipt (amount matches)
   - [ ] Document correction in admin_actions table

5. **Post-Recovery:**
   - [ ] Admin audit of changes (who, what, when)
   - [ ] Customer notification (if > Rp 10,000 affected)
   - [ ] Investigate code bug (update LOGIC_FLOW.md if needed)
   - [ ] Run nightly job again (verify no new imbalances)

**Rollback Plan:**
- Condition: Correction created another imbalance
- Action: Reverse the correction, investigate deeper
- Escalate to CTO/auditor

**Expected RTO**: 30 minutes | **Expected RPO**: 0 minutes (immutable ledger)

### 5.3 SCENARIO 3: RACE CONDITION — 10 DRIVERS ACCEPT 1 ORDER

**Severity**: CRITICAL | **RTO**: 30 minutes | **RPO**: 1 minute

**Symptoms / Detection:**
- Alert: Order assigned to multiple drivers
- Monitoring: ride_orders.driver_id field updated multiple times
- Error: "Multiple drivers assigned to order"
- User Report: 2 drivers showing up

**Impact Assessment:**
- Affected Systems: Ride matching engine
- User Impact: Confusion, both drivers navigating to pickup
- Business Impact: Cancellation fees, customer refund, trust loss

**Immediate Actions (First 15 minutes):**
1. Incident Commander + Ride service owner notified
2. Query affected order details
3. Identify which driver completed delivery (or both did nothing)
4. Calculate refund amount

**Recovery Steps:**

1. **Diagnosis (5 minutes):**
   
   ```sql
   -- Find order with multiple drivers
   SELECT * FROM ride_orders WHERE status = 'DRIVER_ASSIGNED'
   AND driver_id IN (SELECT driver_id FROM ride_orders GROUP BY driver_id HAVING COUNT(*) > 1);
   
   -- Check ride_order_events for multiple assignment attempts
   SELECT * FROM ride_order_events
   WHERE order_id = 'uuid-order-123'
   AND event_type = 'DRIVER_ASSIGNED'
   ORDER BY created_at;
   ```

2. **Identify Actual Driver (10 minutes):**
   - Query: Which driver has location updates after assignment?
   - Query: Which driver completed delivery (status=COMPLETED)?
   - If both: Check payment settlement (who received earnings?)
   - If neither: Cancel both, refund customer

3. **Execution Phase (10 minutes):**

   **Case A: One driver completed delivery (correct)**
   ```sql
   -- Keep this driver, refund other driver's fee
   UPDATE ride_orders SET driver_id = 'uuid-driver-correct' WHERE id = 'order-uuid';
   
   -- Refund incorrect driver's cancellation fee
   INSERT INTO ledger_entries (wallet_id, entry_type, amount, reference_type, reference_id)
   VALUES ('uuid-driver-wrong-wallet', 'CREDIT', 5000, 'RACE_CORRECTION', 'order-uuid');
   INSERT INTO ledger_entries (wallet_id, entry_type, amount, reference_type, reference_id)
   VALUES ('uuid-platform-wallet', 'DEBIT', 5000, 'RACE_CORRECTION', 'order-uuid');
   ```

   **Case B: Both drivers showed up (partial delivery)**
   ```sql
   -- Cancel order, refund all fees
   UPDATE ride_orders SET status = 'CANCELLED' WHERE id = 'order-uuid';
   
   -- Refund escrow amount + driver fees
   INSERT INTO ledger_entries (wallet_id, entry_type, amount, reference_type)
   VALUES ('uuid-customer-wallet', 'CREDIT', 60000, 'RACE_CANCEL_REFUND');
   INSERT INTO ledger_entries (wallet_id, entry_type, amount, reference_type)
   VALUES ('uuid-system-escrow', 'DEBIT', 60000, 'RACE_CANCEL_REFUND');
   ```

4. **Validation Phase (5 minutes):**
   - [ ] Driver count = 1 per order
   - [ ] Ledger entries balanced
   - [ ] Customer notified of resolution
   - [ ] Ledger entries match cancellation fee rules

5. **Post-Recovery:**
   - [ ] Investigate pessimistic lock failure (why 2 drivers got assignment?)
   - [ ] Check statement_timeout (3000ms still applied?)
   - [ ] Verify deadlock retry logic
   - [ ] Run concurrent driver test (k6 script with 10 drivers)
   - [ ] Update DRP.md with findings

**Rollback Plan:**
- If refund creates new imbalance: Reverse refund, escalate to auditor
- If multiple drivers still showing: Manual database correction by DBA

**Expected RTO**: 30 minutes | **Expected RPO**: 1 minute (audit trail preserved)

### 5.4 SCENARIO 4: REDIS CACHE DOWN (LOCKS / IDEMPOTENCY UNAVAILABLE)

**Severity**: HIGH | **RTO**: 30 minutes | **RPO**: N/A (cache, not persistent)

**Symptoms / Detection:**
- Alert: Redis connection refused
- Monitoring: idempotency_cache operations failing
- Error: "Cannot acquire distributed lock"
- Performance: Duplicate requests not detected

**Impact Assessment:**
- Affected Systems: Idempotency, rate limiting, distributed locks
- User Impact: Duplicate wallet transfers possible, transfers slow
- Business Impact: Potential duplicate charges, performance degradation

**Immediate Actions (First 15 minutes):**
1. Check Redis service status (Upstash dashboard or local)
2. Verify DATABASE_URL still working (fallback to PostgreSQL for idempotency)
3. Note: Application can degrade gracefully (idempotency cache optional)

**Recovery Steps:**

1. **Immediate Workaround (2 minutes):**
   - Redis down → Application continues without distributed locks
   - Fallback: Store idempotency keys in PostgreSQL (slower, but safe)
   - Rate limiting degraded (fail-open, allow requests)
   - Alert users: "Experiencing slow transfers, please don't retry"

2. **Diagnosis (5 minutes):**
   ```bash
   # Check if Upstash/Redis is responding
   redis-cli -h <redis-host> -p 6379 PING
   
   # If timeout: Service is down
   # Check Upstash dashboard for alerts
   # Check Render logs for connection errors
   ```

3. **Execution Phase (5 minutes):**

   **Option A: Restart Redis (Upstash managed)**
   - Via Upstash dashboard: Restart button
   - Wait 30 seconds for recovery
   - Test: redis-cli PING → PONG

   **Option B: Reconnect from Application**
   ```bash
   # Render: Restart backend service
   # Via Render dashboard: Deploy → Restart
   # New Redis connection attempt
   ```

4. **Validation Phase (5 minutes):**
   - [ ] Redis PING responds
   - [ ] Idempotency keys can be stored/retrieved
   - [ ] Rate limiting responsive
   - [ ] Transfer operations complete without duplicates

5. **Post-Recovery:**
   - [ ] Monitor Redis metrics (latency, eviction rate)
   - [ ] Check PostgreSQL for leaked idempotency entries
   - [ ] Verify no duplicate transactions during downtime
   - [ ] Update Redis monitoring alerts

**Rollback Plan:**
- N/A (cache degradation is acceptable)
- Fallback: Use PostgreSQL idempotency_cache table

**Expected RTO**: 30 minutes | **Expected RPO**: N/A

### 5.5 SCENARIO 5: BACKEND APPLICATION CRASH (OUT OF MEMORY / PANIC)

**Severity**: HIGH | **RTO**: 5 minutes (auto-restart) | **RPO**: N/A

**Symptoms / Detection:**
- Alert: /health endpoint returns 500 or timeout
- Monitoring: No HTTP responses for 30 seconds
- Error: "OOM killer invoked" in Render logs
- Status: Render shows "Crashed" state

**Impact Assessment:**
- Affected Systems: API services (all endpoints)
- User Impact: Cannot book orders, check balance, complete deliveries
- Business Impact: Order queue backlog, customer frustration

**Immediate Actions (First 5 minutes):**
1. Render auto-restarts container (30 seconds)
2. Monitor /health endpoint recovery
3. Check logs for crash reason

**Recovery Steps:**

1. **Automatic Recovery (30 seconds):**
   - Render health check: GET /health every 60s
   - On failure: Automatic container restart
   - Stateless application → no data loss

2. **If Auto-Restart Fails (5 minutes):**
   ```bash
   # Manual restart via Render dashboard
   Render Dashboard → Services → g-flow-api → Restart
   
   # Or via CLI:
   render restart --service-id <service-id>
   ```

3. **Diagnosis (10 minutes):**
   ```bash
   # Check crash logs
   Render Dashboard → Logs (search "panic" or "OOM")
   
   # Check memory usage history
   Render Dashboard → Metrics → Memory (peak usage)
   
   # Identify cause:
   - OOM: Increase plan RAM (or optimize code)
   - Panic: Debug logs for stack trace
   - Segfault: Go runtime issue (unlikely)
   ```

4. **Long-Term Fix:**
   - If OOM: Optimize queries (add indexes), reduce cache size
   - If panic: Debug panic log, deploy fix
   - If resource exhausted: Upgrade Render plan (from free to paid)

5. **Validation Phase (5 minutes):**
   - [ ] /health returns 200 OK
   - [ ] API responds to requests
   - [ ] No pending errors in logs
   - [ ] Error rate normalized

**Rollback Plan:**
- N/A (stateless service)
- Fallback: Restart service again

**Expected RTO**: 5 minutes (auto) or 15 minutes (manual) | **Expected RPO**: N/A

### 5.6 SCENARIO 6: DATA BREACH (CUSTOMER PII EXPOSED)

**Severity**: CRITICAL | **RTO**: Immediate isolation | **RPO**: N/A

**Symptoms / Detection:**
- Alert: Unusual database queries (SELECT user.national_id, password_hash)
- Monitoring: Large data exports detected
- External: Customer reports receiving phishing emails with leaked data
- Security: 3rd party reports credit card numbers in dark web

**Impact Assessment:**
- Affected Systems: Users, wallets, personal data
- User Impact: Identity theft, financial fraud
- Business Impact: Legal liability, regulatory fines, shutdown risk

**Immediate Actions (First 15 minutes):**
1. **Isolation (5 minutes):**
   - Revoke all API tokens (force re-login)
   - Freeze all accounts temporarily
   - Stop accepting new orders
   - Enable emergency mode (reduced functionality)

2. **Investigation (10 minutes):**
   ```sql
   -- Check access logs for unusual queries
   SELECT * FROM admin_actions WHERE created_at > NOW() - INTERVAL '1 hour'
   ORDER BY created_at DESC;
   
   -- Check for data export attempts
   SELECT * FROM pg_stat_statements WHERE query LIKE '%SELECT%'
   ORDER BY mean_time DESC LIMIT 10;
   ```

3. **Containment (15 minutes):**
   - Change all database passwords (Supabase)
   - Revoke all API keys (Render env vars)
   - Isolate database (firewall rules)
   - Enable WAF rules to block suspicious IPs

**Recovery Steps:**

1. **Forensic Analysis (1-2 hours):**
   - Determine breach scope (which PII exposed?)
   - Identify attack vector (SQL injection? RLS bypass?)
   - Get timeline of access
   - Preserve logs for legal discovery

2. **Notification (24 hours):**
   - GDPR/Local regulations require customer notification
   - Legal team drafts notification
   - Customer communication via email + SMS
   - Status page update

3. **Remediation (1 week):**
   - Fix vulnerability (patch code, add RLS, improve WAF)
   - Reset all passwords (force password change)
   - Rotate encryption keys
   - Audit all third-party integrations

4. **Validation:**
   - [ ] No re-breach indicators in logs
   - [ ] All vulnerabilities patched
   - [ ] Customer notified with remediation steps
   - [ ] Compliance review passed

**Escalation:**
- Immediately contact CTO + Legal team
- Notify hosting provider (Render, Supabase)
- Consider contacting law enforcement (high-value breach)

**Expected RTO**: Immediate | **Expected RPO**: N/A (containment)

### 7.1 Testing Strategy

**Backup Restoration Tests:**
- Frequency: Weekly (Saturday morning)
- Scope: Full database restore to staging
- Success Criteria:
  * Restore time < 30 minutes
  * Data integrity: Row count matches prod
  * Ledger balanced (SUM DEBIT = SUM CREDIT)
  * No corrupted tables
- Owner: Solo developer
- Documentation: Test report → #g-flow-team Slack

**Failover Tests:**
- Frequency: Monthly (first Friday)
- Scope: Simulate Render server crash, auto-restart
- Success Criteria:
  * Failover time < 5 minutes
  * Zero data loss (stateless)
  * All orders in correct state
- Owner: DevOps (Render support)
- Documentation: Test results → DRP_TEST_LOG.md

**Application Smoke Tests:**
- Frequency: After every production deployment
- Scope: Critical user flows (login, book ride, top-up, order food)
- Success Criteria:
  * All endpoints respond 200 OK
  * No error rates > 0.1%
  * Latency < 1s (p95)
- Owner: QA + automated tests (GitHub Actions)

### 9.1 Glossary

- **RTO (Recovery Time Objective)**: Max time system can be down (1h = unacceptable, 4h = acceptable)
- **RPO (Recovery Point Objective)**: Max data loss acceptable (5m = hourly backup, 0m = real-time replication)
- **Backup**: Copy of data for recovery (database snapshots, file archives)
- **Failover**: Switch from primary to standby system (automatic or manual)
- **Disaster**: Event causing system/data unavailable (crash, corruption, breach, hacker, natural disaster)
- **Ledger**: Immutable transaction log (DEBIT/CREDIT entries, never updated)
- **Settlement**: Financial transaction completion (order → driver paid)
- **Escrow**: Temporary fund hold (released after order complete)

### 9.4 Recovery Commands Reference

**Database Recovery (Supabase):**
```bash
# List available backups
supabase db backups list

# Restore from backup
supabase db restore --backup-id <backup-id> --restore-to <new-instance>

# Verify restore
psql -h <new-instance>.supabase.co -U postgres -d g_flow -c "SELECT COUNT(*) FROM wallets"

# Check ledger balance
psql -h <new-instance>.supabase.co -U postgres -d g_flow << 'EOF'
SELECT SUM(amount) FROM ledger_entries WHERE entry_type='DEBIT' as debit,
       SUM(amount) FROM ledger_entries WHERE entry_type='CREDIT' as credit;
EOF
```

**Application Failover (Render):**
```bash
# Check service status
curl https://api.g-flow.com/health

# Restart service
render restart --service-id <service-id>

# View logs
render logs --service-id <service-id> --lines 100

# Update environment variable
render env set --service-id <service-id> DATABASE_URL=<new-url>
```

**Redis Recovery (Upstash):**
```bash
# Test connection
redis-cli -h <redis-host> -p 6379 PING

# Clear idempotency cache (if needed)
redis-cli -h <redis-host> -p 6379 FLUSHDB

# Restart Upstash (via dashboard)
# Console → Restart
```
