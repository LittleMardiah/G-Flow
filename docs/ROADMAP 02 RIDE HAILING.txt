2.2 RIDE BOOKING (F004) — FARE CALCULATION & ESCROW + AUTO-CANCEL WORKER (LOCK HIERARCHY FIXED)
────────────────────────────────────────────────────────────────────────────────

Endpoint: POST /rides/book
  Auth: Required (customer)
  Idempotency: REQUIRED (X-Idempotency-Key)
  Rate Limit: 10 req/min per user

Request:
  {
    "pickup_lat": -6.2088,
    "pickup_lng": 106.8456,
    "dropoff_lat": -6.2950,
    "dropoff_lng": 106.8638,
    "payment_method": "WALLET"  // or "CASH"
  }

Business Logic:

1. VALIDATE — FIXED (Debt Gate Global)
   - Customer wallet status = ACTIVE
   - Coordinates valid (non-null, within range)
   - Pickup != Dropoff
   - ✅ OVERDUE DEBT CHECK (UNIVERSAL): Cek apakah customer memiliki overdue_debt > 0.
     Jika ya, tolak booking dengan status 422 UNPROCESSABLE_ENTITY
     (berlaku untuk WALLET maupun CASH).

2. CALCULATE FARE
   - Haversine distance: distance_km
   - base_fare: Rp 10,000
   - per_km_rate: Rp 4,000 per km
   - estimated_fare = base_fare + (distance_km * per_km_rate)
   - Apply voucher discount (if any)

3. DEDUCT ESCROW (conditional based on payment_method)
   - IF payment_method = 'WALLET':
     - BEGIN TRANSACTION
     - Lock customer wallet: SELECT ... FOR UPDATE
     - Check balance >= estimated_fare
     - Create 2 ledger entries (atomically):
       * DEBIT customer_wallet: estimated_fare
       * CREDIT system_escrow_wallet: estimated_fare
     - COMMIT
   - IF payment_method = 'CASH':
     - ⚠️ JANGAN potong wallet customer saat booking.
     - Validasi customer tidak memiliki overdue debt (sudah di step 1).
     - Dana akan diterima driver secara langsung (offline) saat tiba.
     - Tidak ada escrow deduction.

4. CREATE ORDER
   - INSERT ride_orders:
     * status: CREATED
     * payment_method: sesuai request
     * expires_at: NOW() + INTERVAL '15 minutes'  (ditambahkan)
   - then update to SEARCHING_DRIVER (separate UPDATE)
   - INSERT ride_order_events (from CREATED to SEARCHING_DRIVER)

5. TRIGGER DRIVER MATCHING (async task)
   - Query available drivers within 5km
   - Filter: is_online=TRUE, working_status='IDLE', status='ACTIVE',
            balance >= min_threshold, updated_at >= NOW() - 30s

6. AUTO-CANCEL BACKGROUND WORKER (FIXED — Lock Hierarchy Standardized)

   - Cron job berjalan setiap 1 menit
   - Gunakan Redis distributed lock untuk mencegah multiple instance
   - Query: SELECT id FROM ride_orders 
            WHERE status = 'SEARCHING_DRIVER' 
            AND expires_at < NOW()
   - Untuk setiap order, eksekusi transaksi dengan urutan lock yang KONSISTEN:
     
     a. BEGIN TRANSACTION
     b. SET LOCAL statement_timeout = '3000ms'
     
     c. **Lock order terlebih dahulu** (sesuai standar: order → wallets)
        SELECT * FROM ride_orders WHERE id = $order_id FOR UPDATE NOWAIT
     
     d. Verifikasi status masih SEARCHING_DRIVER (jika tidak, skip)
     
     e. **Lock wallets yang terlibat** (escrow dan customer) dengan ORDER BY id
        SELECT * FROM wallets WHERE id IN (escrow_wallet_id, customer_wallet_id) ORDER BY id FOR UPDATE
     
     f. Update status menjadi 'CANCELLED', cancellation_reason = 'EXPIRED'
     
     g. Insert ride_order_events: SEARCHING_DRIVER → CANCELLED (triggered_by = system)
     
     h. Jika payment_method = 'WALLET':
        - DEBIT system_escrow_wallet: estimated_fare
        - CREDIT customer_wallet: estimated_fare  (full refund)
        - Catat ledger entries
     
     i. COMMIT
   
   - Log jumlah order yang dibatalkan

   **Catatan Lock Hierarchy:** Worker ini mengunci order terlebih dahulu, lalu wallets (diurutkan).
   Tidak ada lock pada users driver, sehingga tidak terjadi deadlock dengan AcceptOrder
   yang mengunci users → order. Urutan lock global: users (jika ada) → order → wallets (ORDER BY id).

Response: 201 Created

2.3 DRIVER DISPATCH MATCHING ENGINE (F005) — CRITICAL RACE CONDITION PREVENTION
────────────────────────────────────────────────────────────────────────────────

** THIS IS THE HARDEST PART OF PHASE 2 **

Challenge:
  10 drivers online simultaneously see order.
  All 10 try to accept at same time.
  → Only 1 should succeed, other 9 get 409 CONFLICT.
  → ZERO double-booking allowed.

Solution: PESSIMISTIC LOCKING (SELECT FOR UPDATE NOWAIT)

Endpoint: POST /rides/{order_id}/accept
  Auth: Required (driver)
  Concurrency: Pessimistic lock with NOWAIT + 3s statement_timeout
  Rate Limit: 30 req/min per driver

Request:
  {
    "driver_id": "uuid-driver-789"
  }

Locking Order Standard (FIXED — Deadlock Prevention + Optimized Lock Scope):
  ⚠️ Untuk mencegah deadlock cross-table, WAJIB menggunakan urutan locking yang konsisten:
  1. Pertama, lock users (baris driver) dengan FOR UPDATE untuk membaca working_status.
     (TIDAK perlu lock wallets jika hanya membaca balance — mengurangi contention)
  2. Kedua, lock ride_orders dengan FOR UPDATE NOWAIT.
  3. Jika ada transaksi lain (misal settlement) yang membutuhkan lock kedua tabel, mereka harus mengikuti urutan yang SAMA.

Implementation (CRITICAL — OPTIMIZED LOCK):

```go
// FIXED: Hapus wallet FOR UPDATE, hanya lock users
func (s *RideService) AcceptOrder(ctx context.Context, orderID uuid.UUID, driverID uuid.UUID) error {
  ctx, cancel := context.WithTimeout(ctx, 3*time.Second)
  defer cancel()

  return s.db.BeginTx(ctx, &sql.TxOptions{
    Isolation: sql.LevelReadCommitted,
  }, func(tx *sql.Tx) error {
    // ============================================================
    // FIXED: Step 1: Lock driver's user (untuk working_status)
    // TIDAK lock wallet — hanya baca balance tanpa lock
    // ============================================================
    var driverWorkingStatus string
    var driverMinBalance decimal.Decimal
    var driverBalance decimal.Decimal

    // Lock user row saja — cukup untuk mencegah perubahan working_status
    err := tx.QueryRowContext(ctx, `
      SELECT working_status, min_balance_threshold
      FROM users
      WHERE id = $1 AND user_type = 'driver' AND status = 'ACTIVE'
      FOR UPDATE NOWAIT
    `, driverID).Scan(&driverWorkingStatus, &driverMinBalance)
    
    if err == sql.ErrNoRows {
      return errors.New("driver not valid (422 UNPROCESSABLE_ENTITY)")
    }
    if err != nil {
      if pgErr, ok := err.(*pgconn.PgError); ok && pgErr.Code == "55P03" {
        return errors.New("lock not available (503 SERVICE_UNAVAILABLE)")
      }
      return err
    }

    // Baca balance tanpa lock (read committed)
    err = tx.QueryRowContext(ctx, `
      SELECT balance FROM wallets
      WHERE user_id = $1 AND wallet_type = 'DRIVER'
    `, driverID).Scan(&driverBalance)
    if err != nil {
      return err
    }

    if driverWorkingStatus != "IDLE" {
      return errors.New("driver is busy (409 CONFLICT)")
    }

    if driverBalance.LessThan(driverMinBalance) {
      return errors.New("insufficient driver balance (422 UNPROCESSABLE_ENTITY)")
    }

    // ============================================================
    // Step 2: Lock ride_orders
    // ============================================================
    var order RideOrder
    err = tx.QueryRowContext(ctx, `
      SELECT id, status, customer_id, customer_wallet_id, estimated_fare
      FROM ride_orders
      WHERE id = $1 AND status = 'SEARCHING_DRIVER'
      FOR UPDATE NOWAIT
    `, orderID).Scan(
      &order.ID, &order.Status, &order.CustomerID, 
      &order.CustomerWalletID, &order.EstimatedFare,
    )
    
    if err == sql.ErrNoRows {
      return errors.New("order not available (409 CONFLICT)")
    }
    if err != nil {
      if pgErr, ok := err.(*pgconn.PgError); ok && pgErr.Code == "55P03" {
        return errors.New("order lock not available (409 CONFLICT)")
      }
      return err
    }

    // 3. UPDATE ORDER: status SEARCHING_DRIVER → DRIVER_ASSIGNED
    _, err = tx.ExecContext(ctx, `
      UPDATE ride_orders
      SET driver_id = $1, status = 'DRIVER_ASSIGNED', assigned_at = NOW()
      WHERE id = $2
    `, driverID, orderID)
    
    if err != nil {
      return err
    }

    // 4. CREATE AUDIT EVENT
    _, err = tx.ExecContext(ctx, `
      INSERT INTO ride_order_events (order_id, from_status, to_status, triggered_by)
      VALUES ($1, 'SEARCHING_DRIVER', 'DRIVER_ASSIGNED', $2)
    `, orderID, driverID)
    
    if err != nil {
      return err
    }

    return nil
  })
}
Why Optimized Lock?
✅ Mengurangi lock contention pada wallet driver (top-up/transfer tidak terblokir)
✅ Hanya lock users untuk mencegah perubahan working_status selama transaksi
✅ Balance dibaca tanpa lock (read committed) — cukup akurat
✅ NOWAIT tetap mencegah race condition pada order

Validation:

Only customer or assigned driver can update

Status must follow state machine

Transitions:

SEARCHING_DRIVER → DRIVER_ASSIGNED (only driver, via /accept)

DRIVER_ASSIGNED → DRIVER_ARRIVED (only driver)

DRIVER_ARRIVED → TRIP_STARTED (only driver)

TRIP_STARTED → COMPLETED (only driver)

COMPLETED → SETTLED (automatic, via trigger)

ANY → CANCELLED (customer anytime, driver before TRIP_STARTED with reason)

Cancellation Logic:

BEFORE DRIVER_ASSIGNED (customer cancel):

Full refund: CREDIT customer wallet = estimated_fare

DEBIT escrow

No fee to driver

AFTER DRIVER_ASSIGNED (customer cancel):

Cancellation fee: Rp 5,000

Refund: CREDIT customer = estimated_fare - 5,000

Fee to driver: CREDIT driver = 5,000

DEBIT escrow for both

AFTER DRIVER_ARRIVED (customer cancel):

Cancellation fee: Rp 10,000

Refund: CREDIT customer = estimated_fare - 10,000

Fee to driver: CREDIT driver = 10,000

DEBIT escrow for both

Driver has waited at pickup location > 5 minutes

Customer did not show up

Cancellation fee: Rp 10,000 from customer wallet

CREDIT driver wallet: Rp 10,000 (full compensation)

DEBIT customer wallet: Rp 10,000

DEBIT escrow (if any) released to customer

Order status becomes CANCELLED

Triggered by driver with reason = 'DRIVER_EMERGENCY'

Hanya berlaku jika status DRIVER_ASSIGNED atau DRIVER_ARRIVED

2.6 DRIVER LOCATION TRACKING — FIXED (Redis ZSET + Timestamp Pruning)
────────────────────────────────────────────────────────────────────────────────

Arsitektur Baru (v2.3 — FIXED Redis Memory Leak):

Masalah v2.2: Menggunakan Expire pada seluruh key set menyebabkan driver offline tetap tersimpan selama ada aktivitas driver lain.

Solusi v2.3: Gunakan Redis Sorted Set (ZSET) dengan Unix timestamp sebagai score, dan lakukan pruning secara periodik.

Driver mengirim lokasi via POST /drivers/{driver_id}/location

Request: { latitude, longitude }

Backend menulis ke Redis menggunakan ZADD:

Key: "driver:locations"

Score: Unix timestamp (detik) saat lokasi diterima

Member: driver_id (berisi koordinat terenkode)

Atau gunakan GEOADD dengan timestamp di member? Lebih baik gunakan ZSET terpisah.

Alternatif implementasi yang direkomendasikan:

Simpan koordinat di Redis Hash dengan TTL per driver:

text
HSET driver:location:{driver_id} lat {lat} lng {lng} updated_at {timestamp}
EXPIRE driver:location:{driver_id} 60
Keuntungan: TTL per driver, tidak perlu cleanup manual.

Query: ambil semua key driver:location:*, filter yang masih ada, lalu hitung jarak.

Namun untuk performa spatial query, gunakan ZSET dengan GEO:

Simpan GEO member dengan format: driver_id:timestamp

Saat query GEORADIUS, ambil semua member, parse timestamp, filter yang <= 60 detik lalu.

Implementasi hybrid yang paling aman:

Gunakan Redis Hash dengan TTL per driver (paling sederhana dan aman dari memory leak).

Untuk spatial query, ambil semua hash key yang masih aktif (scan), lalu hitung jarak di aplikasi (atau gunakan GEOSEARCH jika Redis 6.2+ dengan filter).

Karena dokumen ini untuk MVP, kami pilih opsi sederhana:

Setiap driver memiliki key terpisah: driver:location:{driver_id} dengan TTL 60 detik.

Isi: JSON atau hash dengan lat, lng, updated_at.

Query: scan keys driver:location:*, ambil semua, filter di aplikasi.

Alternatif untuk spatial: gunakan Redis 6.2 GEOSEARCH dengan STOREDIST, tapi tetap perlu filter TTL.

Final decision: Redis Hash + TTL per driver (paling robust terhadap memory leak).

Background worker (cron setiap 5 detik):

Scan semua key driver:location:* yang masih aktif

Batch INSERT ke PostgreSQL driver_locations menggunakan UPSERT (ON CONFLICT DO UPDATE)

Tidak perlu hapus dari Redis, biarkan expire otomatis

Query driver terdekat:

Baca semua driver aktif dari Redis (scan keys dengan TTL)

Hitung jarak di aplikasi (atau gunakan GEOSEARCH jika Redis versi 6.2+)

Fallback ke PostgreSQL jika Redis down (dengan filter updated_at >= NOW() - 30s)

✅ TTL per driver, driver offline otomatis hilang setelah 60 detik
✅ Tidak ada memory leak

✅ Batch flush mengurangi WAL log dan I/O

func (s *DriverService) UpdateLocation(ctx context.Context, driverID string, lat, lng float64) error {
  // Step 1: Write to Redis Hash dengan TTL 60s per driver
  key := fmt.Sprintf("driver:location:%s", driverID)
  err := s.redisClient.HSet(ctx, key, "lat", lat, "lng", lng, "updated_at", time.Now().Unix()).Err()
  if err != nil {
    // Redis down → fallback langsung ke PostgreSQL
    return s.repo.UpsertLocation(ctx, driverID, lat, lng)
  }
  // Set TTL 60 detik
  s.redisClient.Expire(ctx, key, 60*time.Second)
  return nil
}

// Background worker (cron setiap 5s)
func (w *LocationWorker) FlushRedisToDB(ctx context.Context) error {
  // Scan semua key driver:location:*
  var cursor uint64
  var keys []string
  for {
    var err error
    keys, cursor, err = w.redisClient.Scan(ctx, cursor, "driver:location:*", 100).Result()
    if err != nil {
      return err
    }
    // Proses keys
    for _, key := range keys {
      // Ambil data hash
      data, err := w.redisClient.HGetAll(ctx, key).Result()
      if err != nil || len(data) == 0 {
        continue
      }
      driverID := strings.TrimPrefix(key, "driver:location:")
      lat, _ := strconv.ParseFloat(data["lat"], 64)
      lng, _ := strconv.ParseFloat(data["lng"], 64)
      // UPSERT ke PostgreSQL
      w.repo.UpsertLocation(ctx, driverID, lat, lng)
    }
    if cursor == 0 {
      break
    }
  }
  return nil
}

📌 CRITICAL IMPLEMENTATION NOTES — UPDATED v2.3
================================================================================

PESSIMISTIC LOCKING IS MANDATORY — DENGAN OPTIMASI

Use SELECT ... FOR UPDATE NOWAIT dengan 3s statement_timeout

Hanya lock users (untuk working_status), TIDAK lock wallet (hanya baca)

NO optimistic locking or retry loops

If lock not available → return 409 CONFLICT immediately

Lock Ordering Global: users (jika ada) → ride_orders → wallets (ORDER BY id)

IDEMPOTENCY REQUIRED

All POST/PATCH endpoints must support X-Idempotency-Key

Cache responses in Redis for 24h

Return 409 CONFLICT if same key but different params

LEDGER ATOMICITY

Every financial transaction = 2 ledger entries (DEBIT + CREDIT)

Use DEFERRABLE trigger to validate at transaction end

NO exceptions: every rupiah must be accounted for

DRIVER LOCATION — REDIS HASH + TTL PER DRIVER

Setiap driver memiliki key terpisah: driver:location:{driver_id}

TTL 60 detik, driver offline otomatis hilang

Scan keys untuk batch flush ke PostgreSQL

Fallback ke PostgreSQL jika Redis down

Stale data filter: updated_at >= NOW() - 30s

AUTO-CANCEL WORKER — LOCK HIERARCHY STANDAR

Cron setiap 1 menit

Redis distributed lock untuk mencegah multiple instance

Urutan lock: ride_orders → wallets (ORDER BY id)

Tidak mengunci users, aman dari deadlock dengan AcceptOrder

EMERGENCY CANCEL — RESET WORKING_STATUS

Setelah mengubah order ke CANCELLED dengan reason DRIVER_EMERGENCY

WAJIB UPDATE users SET working_status = 'IDLE' WHERE id = driver_id

Dilakukan dalam transaksi yang sama (atomic)

TEST ON REAL DEVICES

Customer app: Test on 2 Android devices (Pixel + Samsung)

Driver app: Test on 1-2 Android devices

DO NOT rely only on emulator (performance differs)

ERROR CODES (Use Consistent HTTP Status)

200: Success

201: Resource created

400: Bad request (validation error)

401: Unauthorized (invalid JWT)

403: Forbidden (insufficient permission)

404: Not found

409: Conflict (race condition, invalid state transition, duplicate request, driver busy)

422: Unprocessable entity (business logic validation failed)

500: Server error

503: Service unavailable (lock timeout)

Before committing code, run:

sql
SELECT reference_id, SUM(CASE WHEN entry_type = 'DEBIT' THEN amount ELSE -amount END) as net
FROM ledger_entries
WHERE reference_type = 'RIDE_SETTLEMENT'
GROUP BY reference_id
HAVING SUM(CASE WHEN entry_type = 'DEBIT' THEN amount ELSE -amount END) != 0;
Result should be empty.

Mobile cold starts should be < 3 seconds.

Profile with Dart DevTools if slow.

Emulator performance is not real device performance.
Pixel 4 (high-end) and Redmi Note 10 (mid-range) both.

text
driver_earning = estimated_fare * 0.80

verify: driver_earning + platform_commission = estimated_fare

Jika driver_balance < -50.000 setelah settlement, jangan biarkan order hang.

Ini mencegah data inconsistency dan menjaga platform tetap berjalan.
