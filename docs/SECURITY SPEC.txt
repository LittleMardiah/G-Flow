2. AUTHENTICATION & AUTHORIZATION
================================================================================

2.1 AUTHENTICATION STRATEGY
────────────────────────────────────────────────────────────────────────────────

METHOD: JWT (JSON Web Token) via Supabase Auth
ALGORITHM: RS256 (asymmetric, RSA 2048-bit minimum)
EXPIRATION:
  - access_token: 1 hour
  - refresh_token: 7 days (stored securely)
  - refresh_token rotation: Every use generates new token

TOKEN CLAIMS (JWT Payload)
{
  "sub": "uuid-user-id",                    // Subject (user ID)
  "email": "user@example.com",              // Email
  "user_type": "customer|driver|merchant|admin|system",
  "phone": "+62812345678",
  "iat": 1723637400,                        // Issued at
  "exp": 1723641000,                        // Expiration
  "iss": "https://supabase-instance.supabase.co",
  "aud": "authenticated"
}

TOKEN STORAGE (Mobile & Web)

🔒 iOS (Flutter):
  - Use Keychain (OS-level secure storage)
  - Never store in UserDefaults or SharedPreferences
  - Code: flutter_secure_storage 9.0.0+

🔒 Android (Flutter):
  - Use KeyStore (OS-level secure storage)
  - Never store in SharedPreferences unencrypted
  - Code: flutter_secure_storage 9.0.0+

🔒 Web (React Admin Panel):
  - HttpOnly cookies for refresh_token (no JS access)
  - In-memory for access_token (cleared on browser close)
  - CSRF tokens for POST/PATCH/DELETE

REFRESH TOKEN FLOW

1. Client stores refresh_token in secure storage
2. After access_token expires (1 hour), client calls:
   POST /auth/refresh-token
   Body: { "refresh_token": "..." }
3. Backend validates refresh_token:
   - Check Supabase sessions table
   - Verify expiration (7 days)
   - Verify user_type hasn't changed
   - Generate NEW refresh_token (rotation)
4. Return: { "access_token": "...", "refresh_token": "..." }
5. Client updates storage with new tokens
6. If refresh fails → Force re-login

2.3 PASSWORD SECURITY
────────────────────────────────────────────────────────────────────────────────

PASSWORD HASHING (Supabase Auth Handles)
  - Algorithm: bcrypt (cost factor ≥ 12)
  - Stored in Supabase auth schema (not in users table)
  - Never transmitted over HTTP (HTTPS only)

PASSWORD REQUIREMENTS
  - Minimum: 8 characters
  - Recommended: 12+ characters
  - Complexity: Mix of upper, lower, numbers, symbols
  - No common patterns (123456, password, etc.)

PASSWORD CHANGE FLOW
  POST /auth/change-password
    Input: { current_password, new_password }
    Validation:
      1. current_password verified against bcrypt hash
      2. new_password != current_password
      3. new_password meets complexity requirements
    Response: HTTP 200 (logout all sessions recommended)

PASSWORD RESET FLOW
  POST /auth/forgot-password
    Input: { email }
    → Generate reset_token (UUID, 1-hour expiry)
    → Send email with reset link
    → Email contains: https://app.g-flow.com/reset?token=...
  
  POST /auth/reset-password
    Input: { reset_token, new_password }
    Validation:
      1. reset_token valid and not expired
      2. Invalidate all active refresh_tokens (logout everywhere)
    Response: HTTP 200

  type EncryptedField struct {
    Value     string // ciphertext
    Algorithm string // "AES256-GCM"
    KeyID     string // KMS key identifier
  }

  func Encrypt(plaintext string, keyID string) (EncryptedField, error) {
    kh, _ := kms.CreateKeyHandle(ctx, keyID)
    a, _ := aead.New(kh)
    ciphertext, _ := a.Encrypt([]byte(plaintext), nil)
    return EncryptedField{
      Value:     base64.StdEncoding.EncodeToString(ciphertext),
      Algorithm: "AES256-GCM",
      KeyID:     keyID,
    }, nil
  }

3.3 SENSITIVE DATA MASKING
────────────────────────────────────────────────────────────────────────────────

IN LOGS (Prevent PII leakage)
  ✅ DO LOG:

    - HTTP status code, endpoint
    - Error code (INSUFFICIENT_BALANCE)
  
  ❌ NEVER LOG:
    - Full email or phone
    - Password or password_hash

4.1 INPUT VALIDATION (Defense Against Injection)
────────────────────────────────────────────────────────────────────────────────

PRINCIPLE: Whitelist & Type Enforcement

String Fields
  Email: RFC 5322 regex
    Pattern: ^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}$
    Max length: 255 characters
    Validation library: github.com/go-playground/validator/v10

  Phone: International format
    Pattern: ^\+?[0-9]{10,15}$
    Max length: 20
    Allowed: +62812345678 or 08123456789

  UUID: RFC 4122 v4
    Pattern: ^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$
    Validation: uuid.Parse(val)

  Name: Alphanumeric + spaces/hyphens
    Pattern: ^[a-zA-Z0-9\s\-']{3,255}$
    Max length: 255

Numeric Fields
  Amount: Non-negative integer (IDR)
    Range: 0 to 999,999,999,999 (Rp 999T)
    Type: int64 (for JSON) → decimal.Decimal (for calculation)
    Decimal places: Exactly 2 (1500.50 not 1500.5 or 1500)

  Coordinates (lat/lng): Decimal with precision
    Latitude: -90 to 90 (8 decimal places)
    Longitude: -180 to 180 (8 decimal places)
    Pattern: ^\-?\d{1,3}\.\d{8}$

Enum Fields (Strict Matching)
  Status: Only values in database ENUM
    Example: order_status ∈ {CREATED, SEARCHING_DRIVER, ..., SETTLED}
    Validation: if !contains(validStatuses, input) { return error }

Date/Time
  Format: ISO 8601 with timezone
    Example: 2026-08-14T10:30:45.123Z
    Validation: time.Parse("2006-01-02T15:04:05.000Z07:00", input)
    Timezone: UTC only (reject other TZ)

PARAMETERIZED QUERIES (SQL Injection Prevention)

❌ NEVER:
  query := fmt.Sprintf("SELECT * FROM wallets WHERE id = '%s'", walletID)

✅ ALWAYS:
  var wallet Wallet
  err := db.QueryRow("SELECT * FROM wallets WHERE id = $1", walletID).
    Scan(&wallet.ID, &wallet.Balance, ...)

Library: pgx/v5 (prepared statements built-in)

  POST /auth/verify-otp: 5 req/min per IP

Read Operations:
  GET * (balance, orders, etc.): 100 req/min per user

Write Operations:
  POST /wallets/*/topup: 10 req/min per user
  POST /wallets/*/transfer: 20 req/min per user
  POST /rides/book: 10 req/min per user
  POST /food-orders: 10 req/min per user
  POST /send-orders: 10 req/min per user

Driver Operations:
  POST /rides/{id}/accept: 30 req/min per driver
  PATCH /rides/{id}/status: 60 req/min per driver

Admin Operations:
  GET /admin/* (read): 30 req/min per admin
  PATCH /admin/* (write): 30 req/min per admin

IMPLEMENTATION (Gin Middleware)

  import "github.com/go-redis/redis/v8"
  
  func RateLimitMiddleware(limit int, window time.Duration) gin.HandlerFunc {
    return func(c *gin.Context) {
      key := "rate:" + getClientID(c)  // user_id or IP
      
      val, _ := redisClient.Incr(ctx, key).Result()
      if val == 1 {
        redisClient.Expire(ctx, key, window)
      }
      
      remaining := limit - int(val)
      c.Header("X-RateLimit-Limit", strconv.Itoa(limit))
      c.Header("X-RateLimit-Remaining", strconv.Itoa(remaining))
      c.Header("X-RateLimit-Reset", strconv.Itoa(int(time.Now().Add(window).Unix())))
      
      if val > int64(limit) {
        c.JSON(429, ErrorResponse("RATE_LIMIT_EXCEEDED"))
        c.Abort()
        return
      }
      c.Next()
    }
  }

GRACEFUL DEGRADATION
  If Redis down:
    - Fail OPEN (allow request) with warning log
    - Continue without rate limiting (not ideal but availability > security)
    - Alert admin to fix Redis

  ON ride_orders FOR UPDATE

5.2 QUERY SECURITY & DEADLOCK PREVENTION
────────────────────────────────────────────────────────────────────────────────

STATEMENT TIMEOUT (Prevent Hanging Locks)

  BEGIN;
    SET LOCAL statement_timeout = '3000ms';  -- 3-second timeout
    SELECT * FROM wallets WHERE id = $1 FOR UPDATE;
    -- ... transaction logic
  COMMIT;

  If lock cannot be acquired in 3s → Connection timeout
  → Automatic retry in application layer (3x max)

DEADLOCK PREVENTION (Golang Implementation)

  func ProcessTransfer(ctx context.Context, from, to uuid.UUID, amount decimal.Decimal) error {
    // CRITICAL: Sort wallet IDs to prevent circular lock ordering
    if from.String() > to.String() {
      from, to = to, from  // Swap to maintain consistent ordering
    }
    
    tx, err := db.BeginTx(ctx, nil)
    if err != nil {
      return err
    }
    defer tx.Rollback()
    
    // Lock in sorted order: FROM then TO
    rows, err := tx.QueryContext(ctx, `
      SELECT id, balance FROM wallets
      WHERE id = ANY($1)
      ORDER BY id
      FOR UPDATE
    `, pq.Array([]uuid.UUID{from, to}))
    
    // Validate balances, insert ledger entries, commit
    return tx.Commit()
  }

  Retry Strategy:
    func RetryOnDeadlock(fn func() error) error {
      for attempt := 1; attempt <= 3; attempt++ {
        err := fn()
        if err == nil {
          return nil
        }
        if strings.Contains(err.Error(), "deadlock detected") {
          backoff := time.Duration(math.Pow(2, float64(attempt))) * 100 * time.Millisecond
          time.Sleep(backoff)
          continue
        }
        return err  // Other error, don't retry
      }
      return errors.New("deadlock retry exhausted")
    }

  type IdempotencyCache struct {

    UserID   string    `db:"user_id"`
    Payload  string    `db:"payload_hash"` // SHA-256
    Response string    `db:"response"`
    Status   string    `db:"status"` // PROCESSING, COMPLETED, FAILED
    ExpiresAt time.Time `db:"expires_at"`
  }

  func CheckIdempotency(ctx context.Context, key string, payload []byte) (*Response, bool, error) {
    // 1. Compute payload hash
    hash := sha256.Sum256(payload)
    hashStr := hex.EncodeToString(hash[:])
    
    // 2. Query cache
    var cached IdempotencyCache
    err := db.QueryRowContext(ctx, `
      SELECT response, status FROM idempotency_cache
      WHERE key = $1 AND expires_at > NOW()
    `, key).Scan(&cached.Response, &cached.Status)
    
    if err == nil {
      // Cache hit
      if cached.Payload != hashStr {
        // Payload mismatch → conflict
        return nil, false, errors.New("IDEMPOTENCY_CONFLICT")
      }
      if cached.Status == "PROCESSING" {
        // Retry (still processing)
        return nil, true, errors.New("PROCESSING")
      }
      // Return cached response
      return &Response{...}, true, nil
    }
    
    // Cache miss → new request
    return nil, false, nil
  }

  Timeout: 24 hours (idempotency_cache.expires_at = NOW() + INTERVAL '24 hours')
  Redis Backup: For fast lookups (AOF persistence enabled)

6.2 ESCROW & SETTLEMENT SECURITY
────────────────────────────────────────────────────────────────────────────────

ESCROW FLOW (Prevent Double-Spending)

Step 1: Customer places order → Escrow amount deducted from wallet
  DEBIT: customer_wallet (Rp X)
  CREDIT: SYSTEM_ESCROW wallet (Rp X)
  Status: CREATED (order held in escrow)

Step 2: Order processing (driver/merchant fulfils)
  Order status transitions: CREATED → ... → COMPLETED

Step 3: Settlement → Money distributed
  DEBIT: SYSTEM_ESCROW (Rp X)
  CREDIT: driver_wallet (Rp Y, ~80%)
  CREDIT: merchant_wallet (Rp Z, ~80%)
  CREDIT: SYSTEM_PLATFORM (Rp W, ~20% commission)
  
  Invariant: Y + Z + W = X (no loss/creation of money)

CANCELLATION REFUND

  If customer cancels before DRIVER_ASSIGNED:
    DEBIT: SYSTEM_ESCROW (Rp X)
    CREDIT: customer_wallet (Rp X)
    (Full refund, no fee)

  If customer cancels after DRIVER_ASSIGNED:
    DEBIT: SYSTEM_ESCROW (Rp X - 5000)
    CREDIT: customer_wallet (Rp X - 5000)
    CREDIT: driver_wallet (Rp 5000)  // Cancellation fee

6.3 DOUBLE-ENTRY BOOKKEEPING (Financial Accuracy)
────────────────────────────────────────────────────────────────────────────────

PRINCIPLE: Every transaction creates exactly 2 ledger entries (DEBIT + CREDIT)

LEDGER TABLE (immutable except is_reversed flag)

  CREATE TABLE ledger_entries (
    id UUID PRIMARY KEY,
    wallet_id UUID NOT NULL,
    entry_type entry_type_enum,  -- DEBIT or CREDIT
    amount NUMERIC(15,2) NOT NULL,
    balance_after NUMERIC(15,2),
    reference_type VARCHAR(50),   -- WALLET_TOPUP, RIDE_SETTLEMENT, etc.
    reference_id UUID,             -- transaction_id or order_id
    is_reversed BOOLEAN DEFAULT FALSE,
    created_at TIMESTAMPTZ DEFAULT NOW(),
    ...
  );

INVARIANT: SUM(DEBIT entries) = SUM(CREDIT entries) (daily verification)

Example Transaction: Customer tops up Rp 500,000

  INSERT INTO ledger_entries (wallet_id, entry_type, amount, reference_type, reference_id, ...)
  VALUES (
    'uuid-bank-gateway',
    'DEBIT',
    500000,
    'WALLET_TOPUP',
    'txn-12345',
    ...
  );
  
  INSERT INTO ledger_entries (wallet_id, entry_type, amount, reference_type, reference_id, ...)
  VALUES (
    'uuid-customer-wallet',
    'CREDIT',
    500000,
    'WALLET_TOPUP',
    'txn-12345',
    ...
  );
  
  -- Verification:
  SELECT
    (SELECT SUM(amount) FROM ledger_entries WHERE entry_type='DEBIT') as total_debit,
    (SELECT SUM(amount) FROM ledger_entries WHERE entry_type='CREDIT') as total_credit;
  
  -- Result: 500000 = 500000 ✓

ADMIN AUDIT (Nightly Job)

  SELECT
    SUM(CASE WHEN entry_type='DEBIT' THEN amount ELSE 0 END) as total_debit,
    SUM(CASE WHEN entry_type='CREDIT' THEN amount ELSE 0 END) as total_credit
  FROM ledger_entries
  WHERE created_at::date = CURRENT_DATE;
  
  If total_debit ≠ total_credit:
    → ALERT: Ledger imbalance detected!
    → Trigger manual audit by admin
    → Notify audit@g-flow.com

9.2 SECRET ROTATION
────────────────────────────────────────────────────────────────────────────────

JWT SIGNING KEY ROTATION (Quarterly)

  1. Generate new key pair (RSA 2048-bit)
     openssl genrsa -out private_key.pem 2048
     openssl rsa -in private_key.pem -pubout -out public_key.pem

  2. Deploy new public key (backward compatible)
     - Old key still validates existing tokens
     - New tokens signed with new key

  3. Wait 1 hour grace period (token expiry)

  4. Rotate private key (active signing key)
     - Only new tokens use new private key

REFRESH TOKEN ROTATION (Every Use)

  POST /auth/refresh-token
    Old refresh_token: abc123xyz
    → Validate old token
    → Generate NEW refresh_token: def456uvw
    → Invalidate old token immediately
    → Return new pair (access_token, refresh_token)

Database Credentials Rotation (Annual)

  1. Create new Supabase backup
  2. Generate new database user + password
  3. Update DATABASE_URL env var
  4. Restart backend servers
  5. Delete old database user

12.3 RUNBOOKS (Quick Reference)
────────────────────────────────────────────────────────────────────────────────

RUNBOOK: Ledger Imbalance

  Severity: CRITICAL

  1. Alert fires: SUM(DEBIT) ≠ SUM(CREDIT)
  2. Incident commander:
     - Page on-call DBA + backend engineer
     - Check nightly_ledger_verification_job logs
  3. Verify imbalance:
     SELECT
       (SELECT SUM(amount) FROM ledger_entries WHERE entry_type='DEBIT') as debit,
       (SELECT SUM(amount) FROM ledger_entries WHERE entry_type='CREDIT') as credit,
       (SELECT SUM(amount) FROM ledger_entries WHERE entry_type='DEBIT') -
       (SELECT SUM(amount) FROM ledger_entries WHERE entry_type='CREDIT') as diff;
  4. Identify transactions in last 24h:
     SELECT * FROM ledger_entries WHERE created_at > NOW() - INTERVAL '24 hours'
     ORDER BY created_at DESC;
  5. Find missing DEBIT or CREDIT entry:
     SELECT * FROM ride_orders WHERE status = 'SETTLED' AND is_settled = false
     UNION
     SELECT * FROM food_orders WHERE status = 'SETTLED' AND is_settled = false;
  6. If missing entry: Insert manually + log action
  7. If orphaned entry: Reverse + investigate code bug
  8. Verify balance again
  9. If balanced: Incident resolved
  10. If not: Escalate to CTO

RUNBOOK: Database Connection Pool Exhausted

  Severity: HIGH

  1. Alert: Active connections >= 14 (of 15 max)
  2. Check slow queries:
     SELECT * FROM pg_stat_statements ORDER BY mean_exec_time DESC LIMIT 5;
  3. Identify culprit (likely SELECT FOR UPDATE lock contention)
  4. Options:
     A. Kill long-running query: SELECT pg_terminate_backend(pid)
     B. Restart backend server (graceful shutdown)
     C. Increase pool timeout (temporary in code)
  5. Monitor connections during fix
  6. Investigate code for deadlock (if recurring)

RUNBOOK: High Error Rate (> 5%)

  Severity: HIGH

  1. Check error types:
     SELECT error_code, COUNT(*) as count FROM errors 
     WHERE created_at > NOW() - INTERVAL '5 minutes'
     GROUP BY error_code ORDER BY count DESC;
  2. Common causes:
     - Database down: Check Supabase status
     - Redis down: Check Redis instance
     - Rate limiting too aggressive: Check metrics
     - Bug in code: Check recent deployments
  3. If database down: Failover or restore from backup
  4. If code bug: Rollback last deployment
  5. Monitor error rate until < 1%
